# M4.24 数据刷新间隔档位（0.5s / 1s / 2s / 3s / 5s）

需求原话：

> 其实我说的挡位是 cpu，gpu 等数据更新时间的挡位，不过这个切换的挡位也保留下来

也就是说：M4.23 做的「切换确认」档位**保留**，另外补一个真正想要的档位 ——
**CPU / GPU / 内存这些数值多久更新一次**。

这一版做了三件事：把刷新间隔做成可调档位（默认仍是 500ms，行为不变）、
修掉「档位一调慢，实际刷新就对不上」的栅格错位、并逐档量化了省电幅度。

编译：0 警告 0 错误（Release，`dotnet build CoPul.sln -c Release`）。

| `SettingsWindow.xaml` | 「采集与网络」卡片首行加**刷新间隔** 0.5s / 1s / 2s / 3s / 5s 分段按钮 |
| `SettingsWindow.xaml.cs` | `SampleRate_Checked`（落盘 + 立即生效 + 回读真实值提示）、`SelectSampleSegment()`、探针命令 `interval:<ms>` |
| `App.xaml.cs` | `SettingsContext.GetSampleInterval/SetSampleInterval`；启动时（采集线程 Start 之前）应用配置；`--sample-interval <ms>` 命令行覆盖（不落盘）；`--stats` 新增 `sample:` 与 `sample flip:` 两行；新增 `--sample-flip <秒>:<ms>` |
| `Sdk/TrendSeries.cs`、`Controls/TrendChart.cs` | 注释更新：容量是**点数**不是时长，档位调慢后折线覆盖的时间按比例变长 |

**默认值不动**（500ms）。升级后行为与 v1 完全一致，要省电才需要主动调慢。

档位表由 `SampleSchedulerOptions.AllowedIntervalsMs` 一处定义，UI 与归一化共用；
手改配置写了 1500 也不会被拒绝 —— `NormalizeInterval()` 归一到最接近的档（1000）。

> **为什么要做成"0.5s 起、只能调慢"**：实际间隔 = max(档位, 各指标自身的 floor)。
> floor 是"这个指标最快只能这么快"（PDH 2ms 一轮、进程列表 20ms 一轮），
> 写 50ms 也不会变成 20Hz，只会被钳住。提示文案里必须说清这一点，
> 否则用户写 5s 生效、写 0.1s 没反应，会觉得是 bug。

## 2. 修掉的真问题：档位一调慢，实际刷新就对不上

第一版接完就去取证，结果 2s / 3s 两档**实测比档位快**：

| 档位 | 第一版实测 | 30s 内发布次数 | 期望次数 |
|---|---|---|---|
| 500ms | 500ms/次 | 60 | 60 ✓ |
| 1000ms | 1000ms/次 | 30 | 30 ✓ |
| **2000ms** | **1667ms/次** | **18** | 15 ✗ |
| **3000ms** | **2144ms/次** | **14** | 10 ✗ |
| 5000ms | 5003ms/次 | 6 | 6 ✓ |

恰好 500 / 1000 / 5000 三档全对，只有 2000 / 3000 错 —— 这不是噪声，是结构性的：

- 各指标有自己的 floor：`T2=1000`、`T2Slow=5000`（硬盘温度）、`T3=10000`、`T2b=5000`（进程/GPU）。
- 实际间隔 = `max(档位, floor)`。档位 2000 时，快层被抬到 2000，而 floor 5000 的两层仍按 **5000** 跑。
- 5000 不是 2000 的整数倍 → 慢层**在快层的两个 tick 之间单独到期**，触发一次"只有它自己"的发布。
- 结果就是整窗多几次重绘，用户看到"我调成 2s，数值却 1.67s 就跳一次"。

而 500 / 1000 / 5000 档下，5000 与 10000 都恰好是档位的整数倍 → 天然同步 → 实测准确。
**这个坑只在"档位开放"之后才存在**（v1 只有 500ms 一档，永远是 500 的整数倍），所以不是回归。

修法：把各层周期**向上对齐到档位的整数倍**，并在档位变更 / 追帧时把相位重排回栅格。

```csharp
int eff = Math.Max(user, floor);
if (user > 0 && eff % user != 0) eff = (eff / user + 1) * user;   // 2s 档下 5s 的层 → 6s
```

代价是慢层比 floor 略慢一点（2s 档下硬盘温度 5s → 6s），换来的是**档位 == 实际刷新节奏**，
而这正是用户调这个档位想拿到的东西。

## 3. 实测（对齐后，五档全对）

`--hidden --stats --seconds 30 --warmup 5`（排除 WPF 渲染，只看采集侧）：

| 档位 | 实测间隔 | 30s 内次数 | 单核 CPU |
|---|---|---|---|
| **500ms（默认）** | 500ms/次 | 60 | 2.030% |
| 1000ms | 1001ms/次 | 30 | 1.874% |
| 2000ms | 2001ms/次 | 15 | 1.718% |
| 3000ms | 3001ms/次 | 10 | 1.406% |
| 5000ms | 5003ms/次 | 6 | 1.562% |

五档实测全部落在档位 ±3ms 内，发布次数与 `wall / 档位` 完全吻合 —— 栅格对齐生效。

### 省电幅度（60 秒长窗口，压掉噪声）

30 秒窗口下各档 CPU 的单调性很差（3000ms 档甚至低于 5000ms 档），
单次采样噪声有 ±0.3pp —— M1.2 那次"0.1pp 级收益被 0.7pp 噪声淹没"的教训在这里同样成立。
所以只对比两端的 60 秒读数：

| 场景 | 500ms 档 | 5000ms 档 | 差值 |
|---|---|---|---|
| `--hidden`（纯采集） | 1.510% 单核 | 1.197% 单核 | **−0.31pp** |
| 带主窗口（采集 + 渲染） | 4.450% 单核 | 3.248% 单核 | **−1.20pp** |
| 其中 UI/渲染线程 | 2.06% | 0.94% | −1.12pp |

结论：**省的主要是渲染，不是采集**。带窗口时降约 27%，折算整机（20 线程）约 0.06% ——
绝对量不大，但对"常年挂着、想把占用压到底"的场景是有意义的，
而且这是唯一一个用户能自己决定"要跟手还是要省"的旋钮。

### 运行中改档位即时生效（P-05）

`--sample-interval 500 --sample-flip 15:3000`（40 秒窗口，第 15 秒翻档）：

```
sample flip : 翻档前 501ms/次（30 次 / 15.0s） → 翻档后 3126ms/次（8 次 / 25.0s，目标 3000ms）
```

前段 501ms、后段 3126ms（8 次 × 3s = 24s，含翻档那一次的相位重排等待）——
**下一个采样 tick 就生效**，不补采、不重启采集线程。设置页那条路径走的是同一个 setter
（探针回读 `interval cfg: 2000 live=2000`）。

## 6. 一个没做的取舍：趋势图要不要固定 60 秒

`TrendSeries` 容量是**点数**（120）不是时长，所以档位调慢后折线覆盖的时间按比例变长
（3s 档 ≈ 6 分钟、5s 档 ≈ 10 分钟）。

保留这个行为：慢档位下要看的本来就是长趋势。真要固定 60 秒就得按档位重建数组，
代价是每次改档位历史被清空 —— 为了"一致"丢掉用户正在看的曲线，不划算。已写进代码注释。
