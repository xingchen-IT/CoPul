## 2. 为什么不能直接复用悬浮窗那套（`WindowGlass`）

那套是为 **34 DIP 高、只有一层半透明 Shell** 的悬浮长条写的，它的三条假设在大窗口上全不成立：

| 假设 | 悬浮窗 | 大窗口（实际） |
| --- | --- | --- |
| 把 `Window.Background` 刷透明就够了 | ✅ 只有 Shell 一层 | ❌ 根 `Border` 另有不透明 `BrushBg`，会把玻璃整个盖住 |
| 内容不会挡住玻璃 | ✅ 无内容 | ❌ 9 张卡片各有一层不透明 `BrushPanel`，占了大半面积 |
| 尺寸固定、不缩放 | ✅ `SizeToContent` | ❌ 可缩放可最大化 |

所以另开一个 `WindowGlassLarge`，并引入**三层遮罩**（见第 4 节）。

## 3. 浓度模型：0–100 连续 + 4 个预设

按用户要求做成连续滑块，同时保留预设档位（快速回到熟悉的浓度）。

**映射不是简单的 0→100 对应 0→100%。** 亚克力层自带约 **17% 固有 tint**（A-40 实测，把 accent alpha 给到 0 也压不掉），所以滑块拉到 0 时仍有 17% 遮盖。若直接线性映射，用户会觉得"拉到 0 却还是有一层东西，是不是坏账"。

显式把这个下限算进去，返回**用户实际看到的遮盖率**：

```
coverage(level) = 1 - (1 - 0.17) * (1 - level/100 * 0.97)
```

实测两端：`level=0 → 17%`、`level=100 → 98%`，与悬浮窗七档实测曲线（17/36/60/77/91/98）对得上。设置页直接把百分比显示在滑块右边，用户不用猜。

| 预设 | 值 | 实际遮盖 |
| --- | --- | --- |
| 很透 | 25 | ~40% |
| 适中 | 60 | ~71% |
| 较实 | 85 | ~88% |
| 最实 | 97 | ~97% |

## 4. 三层遮罩（关键结构）

```
DWM accent 层（窗口后方，负责"模糊"）
  └─ 根 Border 遮罩（浓度旋钮，alpha = coverage）
       └─ 卡片底（card 半透开关决定：不透明 or alpha 跟随浓度）
```

**为什么浓度只调根 Border 的 alpha，不调 accent 的 alpha**：
accent 自带 17% 固有 tint，且改它的 alpha 会连带影响模糊表现；根 Border 是纯上色，行为干净可预测。这与悬浮窗"浓度全交 Shell 遮罩"的取舍一致（A-36 的教训：两个旋钮会互相补偿，排查"这档为什么没变化"要拆两层）。

**卡片半透**的实现走**覆盖本窗口 `Resources` 里的 `BrushPanel`**：
`BlockCard` 样式里的 `{DynamicResource BrushPanel}` 查找顺序是「元素 → 窗口 → 应用」，在本窗口放一份同名键就只影响这个窗口，**设置页拿到的仍是全局那本**。比"逐张卡打标记 + 遍历视觉树改 Background"省事得多，也不会漏掉折叠后重建的卡片。

> 已验证大窗口里只有卡片引用 `BrushPanel`（标题栏与滚动区各用别的键），所以覆盖是安全的。

## 5. 三个把实验带偏过的坑

### 5.1 `Loaded` 在某些启动路径下不触发 → 玻璃静默不生效

第一次加完代码，截图完全看不出玻璃。trace 里连一条 `glass-main` 都没有 —— 说明 `ApplyGlassCore()` 压根没执行。

`ApplyGlassCore` 开头有 `if (_hwnd == IntPtr.Zero) return;`，这是唯一的静默出口。加了一条**无条件日志**才看清：

```
core: hwnd=0x0 enabled=True level=60 cards=False      ← 只有这一次
```

`Loaded` 在 `--shot`（无头截图）等启动路径下**不会触发**，而 `_hwnd` 只在 `OnSourceInitialized` 里赋值。

→ **修法：同时挂 `Loaded` 与 `ContentRendered`**。`ContentRendered` 只要真的渲染了首帧就会到，截图验收依赖它。修后：

```
core: hwnd=0x0 ...        ← Show 之前那次（自测参数，只记状态不施加）
core: hwwnd=0x304D0 ...   ← ContentRendered，hwnd 已就绪
apply level=60 coverage=65% cards=False dark=False mode=Accent Acrylic
```

**教训：** 静默 return 是排查毛玻璃类问题的最大障碍 —— 它不报错、不写日志，和"参数没被采纳"长得一模一样。凡是"必达路径"的守卫，都应该留一条无条件日志。

### 5.2 `--shot`（RTB）截不到 DWM 合成结果 → 假失败

hwnd 修好之后 `--shot` 截图仍然看不出玻璃。这是 **A-35 早就记过的坑**：`RenderTargetBitmap` 只画 WPF 自己的视觉树，DWM 在窗口后方注入的模糊层根本不在其中。

→ 必须用 `--shot-screen`（GDI 抓屏）。**验收毛玻璃两条铁律**：必须抓屏、必须用棋盘格背景（纯色背景糊了也是同一个颜色）。

### 5.3 棋盘格背景板是 Topmost，把主窗口盖住了

`--backdrop` 原本是给悬浮窗小条设计的：居中、`Topmost=true`，因为悬浮窗很小、背景必须在它正下方。

但大窗口 820×1019 比背景板（1200×500）大得多，且背景板 `Topmost` 会**压在主窗口上面**，截出来是一片纯棋盘格。

→ 新增 `--backdrop-behind`：背景板靠左摆（700×500）、**不 Topmost**，让主窗口压在它上面。这样才测得到"窗口下方有图案时玻璃是否模糊"。

### 6.1 性能（A-26：新增渲染面必须测）

毛玻璃是**新增渲染面**，按 A-26 必须复测。

| 轮次 | ON（玻璃开） | OFF（玻璃关） |
| --- | --- | --- |
| 第 1 组 | 1.718% | 1.094% |
| 第 2 组（反序） | 1.354% | 1.823% |
| 配对交替 3 轮 | 2.340 / 2.225 / 1.719 | 1.641 / 2.968 / 1.913 |

**结论：未判定（R24 第五次）。** 理由：**反序结果完全颠倒**（ON 比 OFF 还低），配对交替的三轮里 ON/OFF 区间大幅重叠（ON 1.72–2.34、OFF 1.64–2.97）。这说明读数被环境负载主导，玻璃本身那点增量淹没在噪声里。按纪律不能宣布达标或超标。

**可给的方向判断**：DWM 模糊在 GPU 侧，不占 CPU；`\Process(CoPul)` 口径量不到它。所以玻璃的真实代价主要不在这条指标上（与 M2.1 对 DWM 侧的结论一致：窗口效应被环境合成负载支配，不可分离）。

## 9. 追加变更（2026-11-01 同日，用户要求）

用户两点要求：「将卡片也做成能够自由调节透明度的效果」、「将设置页毛玻璃也合并到外观卡片」。

### 9.1 卡片透明度：布尔开关 → 0–100 可调

原实现是 `GlassCards` 布尔开关（半透/不透明两档），且半透时的 alpha **跟随玻璃浓度**。

**为什么这个设计不够用**：开关只有两个极端，中间没得选：
- 全不透明（100%）→ 玻璃几乎看不见，只剩卡片缝
- 全半透（约 40–60% 随浓度浮动）→ 文字可能发虚

中间那档（如 65–75%）才是多数人真正想要的：卡片还像张卡片，但能看出底下有东西。

**更关键的问题**：「卡片透明度跟随浓度」把两个正交的东西绑在一起了。浓度管的是**背景糊得多实**，卡片管的是**内容承载面多实**。绑在一起就无法表达「窗口很透但卡片要清楚」或「窗口很实但卡片很透」这两种真实需求。

**改法**：拆成两个独立旋钮，`GlassCardOpacity` 0–100 直接映射 alpha（不再乘任何浓度系数）。实测三档：

| 卡片透明度 | 观感 | 截图文件大小（压缩率代理） |
| --- | --- | --- |
| 100% | 完全不透明，只在缝隙见玻璃 | 318 KB |
| 60% | 卡片有存在感、文字清晰、底下图案可见 | 939 KB |
| 25% | 图案通透、接近"内容飘在桌面上" | 1191 KB |

文件大小单调递增 = 背景图案透出越多、压缩率越低，是"透明度真的生效"的硬证据。

**保留了一条保护**：毛玻璃总开关关掉时，卡片**一律回到完全不透明**。没有玻璃层时卡片半透只会透出窗口底色（浑浊的杂灰），那不是玻璃质感，是脏。这条写在代码注释里。

### 9.2 设置页：毛玻璃合并进「外观」卡片

原本是两张独立的卡（「外观」管主题、「毛玻璃」管玻璃）。问题：
- 都在描述"这东西长什么样"，分成两处要来回翻
- 「白底 + 深色玻璃」这类组合在两处各调一半，看不出整体效果

合并后从上到下是四层，由粗到细：**主题 → 分割线 → 毛玻璃开关 → 玻璃浓度（含预设）→ 卡片透明度**。中间用 `BrushDivider` 一条线把「主题」与「毛玻璃」视觉上切开（它们确实是两件事）。

### 9.3 配置迁移（这次改动暴露的真缺陷）

字段从 `GlassCards: bool` 变成 `GlassCardOpacity: int`。老用户的配置里有 `"GlassCards": true` —— 加一个同名新字段读不到它，System.Text.Json 会**静默忽略**，用户的设置直接丢失且无任何提示。

这与 M2 踩过的 `ConfigStore.Save` 手抄字段白名单漏同步是**同一类问题**：字段演化时旧值静默丢失。

**修法**：
```csharp
[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]
[JsonPropertyName("GlassCards")]
public bool? LegacyGlassCardsRaw { get => null; set => LegacyGlassCards = value; }
```
- getter 永远 null + `WhenWritingNull` → 保存时旧字段不会再写回文件
- setter 接住旧值 → 搬到 `LegacyGlassCards`，由 MainWindow 迁移（`true → 40%`、`false → 100%`）
- 迁移后**立刻**回写配置并清标志

**踩到的两个坑**（都实测复现过）：
1. 只写 `get => null` 不够 —— 实测序列化仍会写出 `"GlassCards": null`，把配置文件弄脏
2. 迁移值只在内存里算对了，但 `_config` 里是旧值；用户下次改任一设置触发整份保存时，写下去的还是旧值（迁移算出的 40% 被 75 覆盖）。→ 迁移后必须立刻 `SaveCurrent()`

实测验证：老格式配置 `{"GlassCards": true}` → 启动 → 迁移成 `"GlassCardOpacity": 40`，旧字段从文件中消失，trace 记录 `migrate legacy GlassCards=True -> opacity=40`。
