# M4.10 悬浮窗竖向排列阶段报告

- 日期：2026-10-31
- 范围：6.1 悬浮窗形态扩展 —— 竖向排列
- 用户原话（三轮）：
  1. `为悬浮窗添加一个竖向排列的模式`
  2. `我想要的使原本那种横向的效果旋转90度变成竖向的（字体也要旋转）`
  3. `字体是要正着的` → `竖起来之后宽度太大了`

---

## 1. 需求收敛：三次才定下来

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| v1 | 六格纵向堆叠，每格压成一行（主值左、次值右） | 否 —— 格子内部被重排了，不是"横条转过来" |
| v2 | 整条 `LayoutTransform` 旋转 90°，文字跟着转 | 否 —— 字要歪头读，且失去 ClearType |
| **v3（本版）** | **细高竖条：六项上下排，格内仍是"主值在上、次值在下"两行，文字全部水平正立** | 采用 |

关键在于 v2 和 v3 的区别不是"转不转"，而是**谁承担旋转**：

- v2 让 DWM 转整条 → 形状对，但文字跟着转，用户读不了；
- v3 让**排版**承担"转"（格与格之间从左右排改为上下排），文字本身不转 → 形状和可读性都在。

v2 的那套 `RotateTransform` / `VerticalAngle` / `EstimateVerticalLength`（按条长算）
已经全部删除，没有留开关 —— 留着就是两套尺寸逻辑，迟早对不上。

## 2. 实现

### 2.1 两套面板，`Visibility` 切换

`FloatWindow.xaml` 里 `RowPanel`（横）与 `ColumnPanel`（竖）并存，
同一时刻只有一套参与测量与渲染，折叠的那套成本为零。

竖向用 **`Grid` + 一列 `Auto`**、六行 `Auto`，而不是 `StackPanel`：
一列 `Auto` 会把六个格子都拉到同一宽度，左边界天然对齐；
换成 `StackPanel` 就会因为 `12%` 和 `18.5/31.6G` 长短不一而右侧参差。

### 2.2 尺寸：两个方向都交给内容

| 模式 | 短边 | 长边 | `SizeToContent` |
| --- | --- | --- | --- |
| 横向 | 高 = 34 × 档位（定值） | 宽 = 六格之和 | `Width` |
| 竖向 | — | 宽、高都按内容 | `WidthAndHeight` |

竖向一条边都不手算：宽由最长的那句次值决定，高由「6 × (16 + 13) + 行距 + 内边距」决定。

### 2.3 竖条为什么不可能只有 34 DIP 宽

旋转版的条宽 = 34（= 横向的条高）。文字正立之后，条宽变成"最长那句要横着放下的宽度"：

| 次值 | 10px 时所需宽度 |
| --- | --- |
| `18.5/31.6G`（内存） | 约 53 DIP |
| `v2.7/8.0G`（显存） | 约 42 DIP |
| `51°C` / `NET` / `12ms` | 20～30 DIP |

34 − 内边距 12 − 边框 2 = 20 DIP 的可用宽度，连 `51°C` 都放不下。
**"窄"和"正立"是互斥的**，本版按用户要求选正立。

第一版竖排做出来是 **75 DIP 宽**，用户反馈"太宽"，于是收了两刀：

| 改动 | 效果 |
| --- | --- |
| 左右内边距 10 → 6（`BasePadXCompact`） | 每侧省 4，共 −8 |
| 次值字号 10 → 9（`VerticalLabelRatio = 0.9`，只降次值、不动主值 13） | 最长那句窄约 5 |

合计 **75 → 61 DIP**（−19%），高度不变 229。再往下只能折行或截断，两者都不划算（见 §4）。

### 2.4 首帧 28 → 61：竖排特有的第二次尺寸变化

横向条的列宽是 6.3 的定值，从第一帧起就是 381 宽。竖向宽由内容决定，
而首帧时六格的数据还都是 `—`，窗口只有 28 DIP；采集到第一个快照后
`18.5/31.6G` 一进来才撑到 61。

如果此刻窗口正贴着右边缘，这 33 DIP 会长到屏幕外。所以补了一个尺寸变化后的夹紧：

```csharp
SizeChanged += (_, _) =>
{
    if (!_contentRenderedOnce) return;
    EnsureFullyVisible();   // 幂等，只有出界才真移动
};
```

`ResizeMode=NoResize`，尺寸只会因布局/数据变，不会和用户拖动抢。

### 2.5 顺带修的两处

1. **`PlaceAtBottomLeft`** 用 `ActualHeight`：竖向 `Window.Height` 是 `NaN`，
   `wa.Bottom - NaN` 会让窗口直接消失。
2. **`--float-menu-probe` 的尺寸读数**：`ContentRendered` 那一刻量到的还是 28 宽
   （见 §2.4），会误以为"条子只占了一半"。改为 `Shell.UpdateLayout()` 后测量，
   并把窗口自身尺寸也打出来对比。

## 3. 验收

### 3.1 尺寸随档位等比

| 档位 | 横向 | 竖向 |
| --- | --- | --- |
| 100% | 381×34 | **61×229** |
| 125% | 476×43 | **76×280** |
| 150% | 571×51 | **93×341** |

sidecar 原文（100%）：

```
size : 61×229 DIP
scale: 竖 100% FPS=34.0 CPU=44.0 GPU=44.0 RAM=74.0 VRAM=78.0 NET=44.0 font=13.0/9.0 h=NaN panel=47x212
```

`font=13.0/9.0` 就是"竖排次值缩一档"的证据；横向仍是 `13.0/10.0`。

### 3.2 实拍

- `preview-m4.10-row-vs-col.png` —— 左横右竖并排：字段顺序一一对应
  （FPS → CPU → GPU → 内存 → 显存 → 网络），竖条里每个字都是正的。
- `preview-m4.10-vertical-scales.png` —— 100 / 125 / 150 三档并排，比例一致、无裁切。
- `preview-m4.10-vertical-full.png` —— 100% 档整条（`shot-pad` 外扩，能看到圆角与投影）。

### 3.3 交互

```
place: menu-probe: isOpen=True hit=Border win=28x229 shell=28x229 origin=(1989,0)   ← 首帧量到的窄态
```

`isOpen=True` + `hit=Border`：右键路由事件能把菜单打开，条内一点能被命中
（右键与拖动走同一套命中测试）。`win=28x229` 正是 §2.4 那个首帧窄态，
4 秒后整屏抓图里已经是 61 宽 —— 两个数字对得上，说明"先窄后宽"是数据到位造成的，不是布局错了。

### 3.4 运行中切换与落盘

`--float-persist-probe`（走 setter，与用户点菜单同一条路）：
`"FloatVertical": true` 落盘成功，测试后已还原配置。

设置页「悬浮窗外观 → 排列」横向 / 竖向，改即生效即落盘。

## 4. 已知限制与取舍

1. **宽度下限就是 61 DIP**（100% 档）。再窄只有两条路，都不建议：
   - 让 `18.5/31.6G` 折成两行 → 内存 / 显存两格比别的格多一行，六行高度不齐；
   - 截断成 `18.5/31…` → 丢数值，和"一眼看清"的初衷相反。
2. **首帧会看到一次变宽**（28 → 61）。这是"宽由内容决定"的必然结果，
   横向模式没有这个问题（列宽是定值）。若不能接受，需要在 Show 之前先量一次
   最坏情况的字符串宽度并写死 `MinWidth` —— 那等于把 61 这个数字硬编码，暂不做。
3. **旋转版（v2）的结论保留**：`LayoutTransform` 必须参与测量（`RenderTransform` 会被窗口裁掉）、
   旋转要在设窗口尺寸之前落地 —— 这两条以后若有"真·旋转"需求还能直接用，
   但随之而来的"文字失去 ClearType"没有解法，所以本版不再走那条路。
