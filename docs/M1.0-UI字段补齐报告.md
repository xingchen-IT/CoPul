# M1.0 UI 必需字段补齐报告

时间：2026-10-27
对应里程碑：M1.0（M1 大窗口的前置步骤）
关联文档：`CoPul-需求规格说明书-v0.9.md` 第 2.3 / 3.2 / 4.1 / 4.3 / 4.4 / 16 章

## 1. 为什么要先做这一步

需求文档 5.3「大窗口字段清单」要求展示 30 余项字段，M0.6 落地的采集层只覆盖 26 项。开工 M1 之前先对了一遍账，发现 **5.3 里点名要显示的字段有 9 项在采集层根本不存在**——不是"没显示"，是"没采"：

| 字段 | 文档 ID | M0.6 结束时状态 |
| --- | --- | --- |
| CPU 型号 | C01 | 枚举里有 `CpuName`，**没有任何 Provider 写它** |
| 各核心占用率（20 格） | C03 | 完全没做，PDH 只取了 `_Total` |
| 负载均值 1/5/15 | C10 | 没做 |
| GPU 型号 | G01 | `NvmlGpuProvider.DeviceName` 有值，但没进快照 |
| 已缓存（Standby） | M04 | 没做；`RamSwapUsedMb` 是死枚举，且注释编号与 4.3 错位 |
| 提交量（Commit） | M05 | 没做 |
| 页面文件使用 | M06 | 没做 |
| 物理盘型号/类型/容量 | D01 | 没做 |
| 分区使用率 | D04 | 没做 |

还有一个结构性问题：`MetricSnapshot` 只承载 `double` 与 `double[]`，而 C01 / G01 / D01 / D04 是字符串与结构体。硬塞进去会让每次 tick 的 `Clone()` 多复制一遍永不变化的内容。

**做法**：先写探测程序 `tools/m10/probe` 把三条候选路径全部实测，再按数据选型、改采集层、复测开销。没有一条路径是按文档原文直接写的——三条都改了，理由在下面。

## 2. 结论摘要

| 项 | 结论 | 关键数据 |
| --- | --- | --- |
| C03 每核占用 | **保持文档原方案（PDH 每核）**，不改用 NtQuerySystemInformation | 边际成本 +0.11 ms/tick（整机 0.001%），换来与 C02 同口径 |

## 3. 三条路径的实测与选型

### 3.1 C03 每核占用率：为什么最后没换成更便宜的那条

文档 4.1 原写「PDH 每逻辑核」。真正动手前先量了两条路：

| 路径 | 单次成本（20 核） | 口径 |
| --- | --- | --- |
| PDH 每核 20 个计数器 | **+0.11 ms/tick**（见下） | `% Processor Utility`（与 C02 一致） |
| `NtQuerySystemInformation(8)` | **48 µs/call**，一次系统调用拿全部核 | `% Processor Time`（与 C02 不一致） |

NtQuery 便宜约 20 倍，但口径不同：`% Processor Time` 在睿频时会超 100%，`% Processor Utility` 与任务管理器一致（Q-06 已定）。两者在大窗口里并排显示时会出现"总占用 35%，20 格加起来 50%"，用户只会当成 bug。

**决定：保留 PDH 每核。** 理由是 0.11 ms 的差距在整机口径下是 0.001%，而口径不一致是每天都会被看见的问题。

PDH 方案的实测细节（`tools/m10/probe` B2/B3 节，同一台机器、同一进程）：

```
计数器  9 个（OsProvider 原有集合）：Collect 1.961 ms   Collect+格式化 2.016 ms
计数器 29 个（+20 个每核）          ：Collect 2.163 ms   Collect+格式化 2.125 ms
→ C03 的边际成本 = 0.109 ms/tick
```

顺带纠正一个此前的推断：A-16 里写「PDH 约 0.2 ms/计数器」，是**按个数线性外推**得到的，实测不成立。9 个计数器要 1.96 ms，再加 20 个只要 2.16 ms——成本由**计数器族**决定，不是个数。`PhysicalDisk` 与 `Network Interface` 两个族每次 `Collect` 都要去问驱动，`Processor Information` 只是读内核共享内存，两者差两个数量级。这条结论直接影响以后做预算的方式（见 3.4）。

### 3.2 D01 物理盘：零访问权限 IOCTL 胜出，两个理由

三条候选路径全部实测：

| 路径 | 不提权可用 | 成本 | 问题 |
| --- | --- | --- | --- |
| WMI `Win32_DiskDrive` | 是 | 首次 20–200 ms | A-05 排除 WMI 轮询；要引 `System.Management` |
| SetupAPI `SetupDiGetClassDevs` | 是 | 4.5 ms / 2 盘 | **返回顺序与 `PhysicalDriveN` 索引不对应** |
| `\\.\PhysicalDriveN` 零权限 IOCTL | 是 | 4.4 ms / 16 次探测 | 无 |

第三个方案的第二个理由是决定性的：硬盘温度（D02）是**按 `PhysicalDriveN` 顺序排成的数组**，如果盘列表来自 SetupAPI，而温度数组来自 NVMe Provider，两块盘的型号和温度会错位——用户看到"Predator 32°C / 三星 48°C"时不会怀疑是排序错了。

代价是两条 IOCTL 的细节，都踩过：

- **容量不能用 `IOCTL_DISK_GET_LENGTH_INFO`**：零访问权限下返回 `ERROR_ACCESS_DENIED(5)`。必须用 `IOCTL_DISK_GET_DRIVE_GEOMETRY_EX`，`DiskSize` 在缓冲区偏移 **24**（`DISK_GEOMETRY` 占 24 字节，8 字节对齐）。
- **型号用 `STORAGE_DEVICE_DESCRIPTOR`**：零权限可用，`VendorIdOffset(12)` / `ProductIdOffset(16)` / `BusType(28)`。`BusType` 直接给出 NVMe / SATA / USB，不用再从实例 ID 里猜。

实测输出：

```
#0 [NVMe] NVMe SAMSUNG MZVL81T0HELB-00BTW  953.9 GB
#1 [NVMe] NVMe Predator SSD GM7 1TB         953.9 GB
```

### 3.3 M04–M06 与 C10

`GetPerformanceInfo` 一次调用同时给出 `SystemCache`（已缓存）/ `CommitTotal`+`CommitLimit`（提交）/ `PhysicalTotal`（算页面文件），36 µs。

**M06「页面文件使用」是推算值**：`(CommitTotal − PhysicalTotal) × PageSize`。提交量超过物理内存的部分必然落在页面文件或压缩内存里，所以它不是"页面文件单独占了多少"。精确值要走 `NtQuerySystemInformation(SystemPageFileInformation)`，v1 不做——但 `MetricSample.Note` 里必须带上这句，不能让 UI 把它当精确读数显示。

C10 用 `GetSystemTimes` 做 60/300/900 秒时间常数的指数平滑（`α = 1 − e^(−Δt/τ)`）。**Windows 没有 load average**，这与 Linux 的 uptime 语义接近但不是同一算法，文档里也不该写成"负载均值 = 运行队列长度"。

### 3.4 静态信息为什么不进 MetricSnapshot

`SampleScheduler.Merge()` 每个 tick 都 `Clone()` 整份快照再逐项覆盖。把型号、盘列表、分区列表塞进快照，等于每 500 ms 复制一遍永不变化的字符串——0.5s 档下每秒 2 次，纯浪费。

所以新增 `Metrics/SystemInfo.cs`：启动时 `Collect()` 一次，`CpuName` / `Disks` / `Partitions` / `OsVersion` 全在里面，`GpuName` 由 `NvmlGpuProvider.DeviceName` 回填。分段耗时：

```
总计 6.84 ms（CPU名 0.81 / 物理盘 4.43 / 分区 1.56）
```

**首次调用是 188.89 ms**——那是 JIT 与程序集冷启动，同一进程第二次起就是 6.8 ms。这恰好是 A-12 要求"初始化必须异步"的又一个证据：A-12 的理由原本是 `Computer.Open()` 3532 ms，现在是"哪怕 6.8 ms 也不该放在 UI 线程上"。

## 4. 开销回归

### 4.1 同机 A/B（30 秒 × 2 轮，非提权）

| 轮次 | C03 | 进程 CPU（单核） |
| --- | --- | --- |
| 1 | 关 | 0.469% |
| 1 | 开 | 0.625% |
| 2 | 关 | 0.729% |
| 2 | 开 | 0.521% |

**开与关的区间完全重叠**（0.469–0.729 vs 0.521–0.625），30 秒窗口分辨不出 C03 的成本。这与 3.1 的 0.11 ms/tick（整机 0.001%）一致。

### 4.2 正式复测（提权，60 秒 × 3 轮，`--steady-only 500 --repeat 3`）

| 轮次 | 进程 CPU 单核 | 整机 |
| --- | --- | --- |
| 1 | 0.391% | 0.020% |
| 2 | **0.573%** | 0.029% |
| 3 | 0.469% | 0.023% |

对照改动前（M0.6，同样 60 秒 × 3 轮）：0.208 / 0.521 / **0.625**。

- 中位 0.521 → **0.469**，最坏 0.625 → **0.573**
- 对 0.9% 目标余量 **1.57 倍**（按最坏值）
- **不能说"变快了"**：R18 已确认 0.5s 档读数离散达 3 倍，这次的新旧两组落在同一离散范围内，正确表述是"未检出回归"

逐层 tick 时间这轮比 M0.6 高（T1b 4.3–4.9 ms vs 2.29 ms，T2s 13–15 ms vs 12.5 ms），但进程 CPU 反而略低。原因是机器当时在跑构建与浏览器，`SetThreadAffinityMask` 遇到争用会更久——**跨会话的 tick 时间不可比，只有进程 CPU 可比**。这条要写进验收方法，否则下次又会有人拿两个月的日志对比 tick。

## 5. 踩到的坑

| 坑 | 现象 | 根因 | 教训 |
| --- | --- | --- | --- |
| `GetDiskFreeSpaceExW` 漏写 `CharSet.Unicode` | 三个卷全部 `ERROR_PATH_NOT_FOUND(3)`，`DriveInfo.IsReady` 却都是 True | 默认 `CharSet.Ansi`，把 `"C:\"` 按 ANSI 塞进宽字符参数，系统看到 `"C\0"` | **所有带字符串参数的 Win32 P/Invoke 必须显式声明 CharSet**（→ A-21） |
| 漏测逐计数器格式化 | 探测显示 C03 只要 +0.17 ms，真实 T0b 却像涨了 1.7 ms | 只测了 `PdhCollectQueryData`，没测 20 次 `PdhGetFormattedCounterValue` | **测成本要测完整调用路径**，只测其中一段会低估一个数量级 |
| T0b 3.4 ms 被当成 C03 的锅 | 差点为此推翻 PDH 方案 | 机器在跑构建，`PhysicalDisk` 族的 Collect 变贵 | 归因必须同机 A/B，不能拿两次独立运行的 tick 相减 |
| PDH 实例名字典序 | 20 格顺序会变成 0,0 / 0,1 / 0,10 / 0,11 / … / 0,2 | `PdhExpandWildCardPath` 按字典序返回 | 必须按 `(处理器组, 逻辑核)` 数值重排（→ A-20） |
| 首次 `SystemInfo.Collect()` 188 ms | 以为静态信息很贵 | ~~JIT + 程序集冷启动~~ → **v0.10 更正为冷盘唤醒**，见 8.5 | 冷启动数据不能当稳态数据（与 m06 的"15 秒预热"同一条教训）；归因没查清前不要写进结论 |

## 8. R19：G01 的 DXGI 兜底（v0.10 补充）

### 8.1 问题

`NvmlGpuProvider` 在三种情况下拿不到型号：没有 `nvml.dll`（AMD / Intel 机器）、`nvmlInit` 返回非零（老驱动 / 服务被禁 / 容器内）、`nvmlDeviceGetCount` 为 0。这三种情况原本都会让 G01 变成空串，而 4.2 承诺"非 NVIDIA 平台也保证 G01"——等于用 UI 掩盖一个已知缺口。

补法：`CreateDXGIFactory1` + `IDXGIFactory1::EnumAdapters1` + `IDXGIAdapter1::GetDesc1` 拿 `DXGI_ADAPTER_DESC1.Description`。选它的理由是**不提权、不建 D3D 设备、不依赖 LHM**——WMI 首次查询 20–200 ms 且违反 A-05，LHM 需要管理员。

### 8.2 三个必须写下来的坑

| 坑 | 现象 | 根因 | 处理 |
| --- | --- | --- | --- |
| **同一块卡被列 4 次** | 适配器列表里出现 4 条一模一样的 RTX 4060 | 同一物理卡的不同输出通路各挂一个适配器实例；**且 4 个条目的 LUID 全不一样**（`0x106ED / 0x1E695 / 0x1E2A2 / 0x1A956`） | 第一版按 LUID 去重，等于没去重（剩 5 条）。改用「型号 + `SubSysId` + 独显容量」为键（→ A-23） |
| **软件渲染器混进来** | `Microsoft Basic Render Driver`（`vid=0x1414`）被当成一张卡 | 无独显 / 远程桌面环境会暴露 WARP | 按 `DXGI_ADAPTER_FLAG_SOFTWARE`（`Flags & 2`）剔除 |
| **索引 0 不保证是独显** | 本机恰好是 NVIDIA 在前 | DXGI 枚举顺序无契约 | 按 **独显容量降序**取第一块；容量全 0（纯核显）时取第一块。完整列表留在 `SystemInfo.GpuAdapters` 供 UI 展开 |

另外 `DXGI_ADAPTER_DESC1` 里既有 `ByValTStr SizeConst=128` 又有非 blittable 的 `SIZE_T`，结构体必须严格按顺序声明、`AdapterLuid` 用 `long` 占位对齐——字段错一位，型号读出来就是乱码或空串。

### 8.3 耗时

| 场景 | 耗时 | 说明 |
| --- | --- | --- |
| 首次 `SystemInfo.Collect()`（盘是热的） | **45.0 – 68.1 ms** | 其中 DXGI **37.8 – 61.6 ms**，绝大部分是 `dxgi.dll` 加载与显示栈初始化 |
| 首次 `SystemInfo.Collect()`（**冷盘**） | **229.9 – 235.5 ms** | 多出来的 ~190 ms 全是物理盘唤醒，见 8.5 |
| 同进程第二次 `Collect()` | **1.7 – 3.1 ms** | 其中 DXGI **1.0 – 2.3 ms**，这才是枚举本身的成本 |
| 物理盘枚举（热盘） | 首次 3.5–4.6 ms，热 0.13–0.23 ms | — |

**只在启动跑一次，不进采集循环**，所以 0.5s 档的 0.573% 基线不受影响，本轮没有再跑 60 秒窗口。在真实的 WPF 进程里 `dxgi.dll` 通常已被 WPF 自己加载，实际增量应小于上表。

### 8.4 验收

| 场景 | G01 | 来源 | 证据 |
| --- | --- | --- | --- |
| 本机正常路径（NVML 可用） | `NVIDIA GeForce RTX 4060 Laptop GPU` | `NVML` | `tools/m10/raw/r19-verify.txt` |
| `--no-nvml`（模拟非 NVIDIA / nvmlInit 失败） | `NVIDIA GeForce RTX 4060 Laptop GPU` | `DXGI` | `tools/m10/raw/r19-no-nvml.txt` |

`--no-nvml` 只是禁止 NVML 覆盖 G01，不改变 NVML 是否初始化——它验证的是"**NVML 没给出名字时，G01 是否仍有值**"这条代码路径；与非 NVIDIA 机器的差别仅在于 DXGI 报出来的厂商名不同。

### 8.5 顺带查清的一个坑：物理盘首次访问会被"冷盘"拖到 190 ms

| 盘的状态 | 物理盘枚举耗时 | 复现方式 |
| --- | --- | --- |
| **冷盘**（空闲几十秒以上） | **186.9 – 194.1 ms** | 静置 90 秒后跑一次，稳定复现 |
| 热盘（连续访问） | 3.5 – 4.6 ms | 连跑 5 次，5 次都是热态 |
| 同进程第二次 | 0.13 – 0.23 ms | `--static-twice` |

一开始误判成"Bash 通道的沙箱在拦设备 I/O"——因为在 Bash 里跑到的正是 193 ms，而紧接着在 PowerShell 里连跑三次只有 3.4–4.4 ms。静置 90 秒后用 PowerShell 复现到 193.7 ms，才确认**与通道无关，与盘是否睡着有关**：NVMe 进低功耗后第一次 `CreateFile` / `DeviceIoControl` 要等唤醒，190 ms 与这类唤醒延迟同量级。本轮没拆到 `CreateFile` 与 `DeviceIoControl` 各自的耗时，根因留作定性结论。

对 M1 的影响：**磁盘区块的首个值可能晚 ~190 ms 到**（启动瞬间盘通常是醒的，用户中途打开 CoPul 时才会遇到）。这不是缺陷，但它把 A-12（静态信息必须放后台线程）从"建议"变成了硬要求——190 ms 卡在 UI 线程上就是肉眼可见的界面迟滞。
