# M1.4 报告：使用率趋势图 + 进程统计区块

日期：2026-10-27  
需求文档版本：v0.15（5.2 布局图与 5.3 字段清单补 trend / proc 两个区块）

## 1. 交付内容

| 功能 | 位置 | 说明 |
|---|---|---|
| 趋势区块（`trend`） | GPU 与内存之间 | CPU / GPU 使用率折线，近 60 秒，纵轴固定 0–100%，可折叠 |
| 进程区块（`proc`） | 硬盘下方 | 占用最高的 8 个进程：名称 / PID / CPU% / GPU% / 内存，5 秒刷新，可折叠 |

两块都接入了折叠持久化（config `collapsedBlocks`），且**折叠进程区块时整组采集会停掉**
（`CollectorHost.ProcessSamplingEnabled`）——这两组合计约 20ms/轮，是全程序最贵的采集，
看不见就不该采。

截图：`docs/preview-m1.4-trend.png`（趋势图）、`docs/preview-m1.4-proc.png`（进程表，中间区块临时折叠以便入镜）。

## 2. 采集层选型（先探测、后落地）

探测程序：`tools/m13/probe`（M13Probe），验收程序：`tools/m13/verify`（M13Verify）。
本机 460+ 进程、20 逻辑核，全部实测。

### 2.1 每进程 CPU + 内存：NtQuerySystemInformation

| 候选 | 本机实测 | 结论 |
|---|---|---|
| `Process.GetProcesses()` + 逐进程句柄 | 数百次 OpenProcess/GetProcessTimes | 未实测，理论更贵 |
| PDH `\Process(*)\% Processor Time`（469 实例） | 一轮 9.10 ms | 备选 |
| **NtQuerySystemInformation(SystemProcessInformation)** | **一轮中位 10.5 ms（472 进程）** | **采用** |

成本拆解（`probe split`）：走链表 0.05ms，**几乎全部成本在系统调用本身**，托管侧没有优化空间。

**口径（关键）**：CPU% = ΔCPU时间 / Δ墙钟 / 逻辑核数。**必须除以核数**，否则单线程跑满
会显示 100%（任务管理器显示 5%）。本机 PDH `_total` 实测 1993.93 ≈ 20 × 100，正好印证
PDH 给的也是「每核 100」口径。

内存用 `WorkingSetPrivateSize`（偏移 8）= 任务管理器「内存」列的私有工作集，不是提交大小。

**正确性交叉验证**（`M13Verify` 与 PDH 同期对照，5 秒窗口 ÷ 20 核）：

| 进程 | CoPul | PDH |
|---|---|---|
| g112-Win64-Shipping | 9.5% | 8.6% |
| python | 4.9% | 4.7% |
| WorkBuddy | 4.0% | 4.3% |
| DeepSeek Harness | 4.0% | 3.8% |
| wallpaperui | 2.7% | 2.7% |
| msedgewebview2 | 2.1% | 2.2% |

排序与数值全部在 ±1pp 内吻合。结构体偏移写错会有天文数字，解析侧做了健全性检查
（PID / CPU 时间 / 私有工作集越界即整帧丢弃），并有 4096 次的链表遍历上限保护。

### 2.2 每进程 GPU：只有 Windows GPU Engine 计数器一条路

| 候选 | 实测结果 |
|---|---|
| NVML `nvmlDeviceGetProcessUtilization` | **rc=7 NOT_SUPPORTED** |
| NVML `nvmlDeviceGetComputeRunningProcesses` | 成功但 `usedGpuMemory` 全是 0xFFFFFFFFFFFFFFFF（值不可用，nvidia-smi 同样 `[N/A]`） |
| **PDH `\GPU Engine(*)\Utilization Percentage`** | **可用，1045 实例** |

WDDM 显卡（笔记本几乎全是）拿不到 NVML 每进程数据是**固有限制，不是权限问题**。

三个降本手段：

1. **按引擎类型裁剪**：只留 3D / VideoDecode / VideoEncode / VideoProcessing / Compute
   （跳过 Copy 299 / LegacyOverlay 54 / Security 98 / VR 49），
   1045 实例一轮 25ms → **456 实例 9.6ms**；
2. **部分通配符展开**：`\GPU Engine(*_engtype_3D)\...` 一次 9ms，
   全量展开要 0.5–1s；
3. **引擎求和后钳到 100%**：多引擎并行时求和可能超 100。

每进程 GPU 初始化耗时 600–740ms（首次展开要加载 GPU Engine 提供者），发生在后台初始化线程，
不阻塞窗口。GPU 列从第 3 个采样周期（约 10–15s）开始有值。

### 2.3 调度

新增 `Tier.T2b`，floor 5000ms（`Proc.List` + `Proc.Gpu` 两个组，同 tick 跑完）：

| 放进 | 折算单核 |
|---|---|
| T2（1000ms）❌ | 20ms / 1s = **2%**，超整窗预算 |
| **T2b（5000ms）✅** | 20ms / 5s ≈ **0.40%** |

## 3. 展示层

### 3.1 TrendChart（自绘折线图）

不引第三方图表库：每 0.5s 重画一次，图表库的坐标轴/图例/动画全是白花；
只需要两条折线 + 三条网格线，DrawingContext 直画约 0.1ms。

- 纵轴**固定 0–100%**，不做自动缩放——自动缩放会把 5% 的抖动画成满载；
- 数据不足时**从右侧画起**，旧数据从左侧长出来（新点永远贴右边）；
- CPU 线带浅色面积填充（仅 CPU，双填充会糊），GPU 纯线条；
- 数据源 `TrendSeries`：环形缓冲 120 点，NaN 断线不画 0（A-13）；
- 画刷 / 画笔全部缓存并 Freeze。

### 3.2 进程表

行对象复用（同 DiskRow 套路）：多退少补、只改字段，避免每 5s 重建整表视觉元素。
CPU < 10% 显示一位小数；首次差分算不出显示 `—`；排序取 **max(CPU, GPU)**——
只按 CPU 排的话，硬解码/跑游戏但主逻辑闲的进程永远排不上来。

## 4. 编译与验证

- `dotnet build -c Release`：**0 警告 0 错误**；
- `M13Verify` 三轮采样：CPU 与 PDH 对照吻合（见 2.1 表），GPU 第 3 轮出值
  （g112 10%、dwm 3%、DeepSeek 3%、msedgewebview2 1%）；
- `--shot` 渲染：趋势图数据从右侧生长符合设计，进程表数值与任务管理器一致。
