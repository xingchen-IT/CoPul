# M4.53 公开前的隐私扫描与历史重写

> 2026-11-05。仓库转公开前的最后一次体检。结论：文件内容基本干净，**但 148 个提交的作者邮箱
> 全是作者的个人 QQ 邮箱** —— 一旦公开，`git log` 一眼可见，配合 Gitee 账号能直接锁定到人。
> 当晚做了全历史重写。

## 1. 怎么扫的

三层，缺一不可：

| 层 | 方法 | 覆盖 |
| --- | --- | --- |
| 当前树 | `git grep` 逐模式 | HEAD 上 439 个文件 |
| **全历史** | `git rev-list --all --objects` + `cat-file --batch` 批量取内容 | **783 个文本 blob**（含已删除文件） |
| 提交元数据 | `git log --all --format='%ae %ce'` | 148 个提交的作者与提交者 |

第二层是关键：只扫 `HEAD` 会漏掉"曾经提交过、后来删掉"的文件，那些内容仍躺在历史里，
`git clone` 照样拉得到。

扫描维度：机器名 / 用户目录路径 / 用户名 / 邮箱 / 手机号 / 身份证 / 内网 IP / 凭据关键词 /
MAC 地址 / 工作盘路径。

| 项目 | 结果 | 判定 |

| 手机号 / 身份证 / 真实姓名 / 学号 | 0 | ✅ |

实际内容止于「网络」卡，进程表在更下方，没被截进去。

## 3. 决定与代价

只脱敏文件、不动提交邮箱是不彻底的 —— 泄漏的是元数据，而元数据藏不住。选了重写。

**代价是显性的**：

| 项 | 变化 |
| --- | --- |
| 148 个提交 | **SHA 全部改变** |
| `v0.1.1` 标签 | 从 `d6a6d08` 变为 `553a9a3`（附注标签对象 `5127400`） |
| 远端 main | `2a32238` → `88586b6`，需 force push |
| Gitee 发行版 v0.1.1 | 标签指向变了，需到发行版页面确认仍能打开 |
| 已发布安装包里的 `BUILD-INFO.txt` | 记录的旧 SHA 在新历史里**不存在** |

最后一条是遗留瑕疵：0.1.1 安装包内的 `BUILD-INFO.txt` 写着构建时的提交号（旧历史），
重写后查不到。对应源码本身是完整的（就在 `v0.1.1` 标签指向的提交里，内容与旧提交一致，
只是 SHA 变了），GPL-3.0 §6 的"提供对应源码"不受影响，但**sha 对不上**这件事得知道。

## 4. 怎么做的

工具用 `git filter-repo`（官方推荐的 filter-branch 替代品，单个 Python 脚本，208 KB，
下载自上游 raw）。两条规则：

```text
# mailmap.txt —— 只换邮箱，不动名字
xingchen <16982100+stardust-xingchenya@user.noreply.gitee.com> xingchen <旧个人邮箱>
星尘     <16982100+stardust-xingchenya@user.noreply.gitee.com> 星尘     <旧个人邮箱>

# replace-text.txt —— 替换 blob 内容（左边是真实值，此处脱敏）
<真实计算机名>==>LAPTOP-XXXXXXXX
C:\Users\<真实用户名>==>C:\Users\user
C:/Users/<真实用户名>==>C:/Users/user
```

新邮箱是 Gitee 的隐私地址格式 `{用户ID}+{用户名}@user.noreply.gitee.com`（ID 从公开 API
`/api/v5/users/{用户名}` 取到）。用它提交**贡献度仍归到账号**，但 `git log` 里看不到真实邮箱。

**先在副本上试跑**，确认只动了 4 个文件、5 行，全在预期位置，才动正式仓库。正式仓库改写前
`git bundle create --all` 存了 13 MB 全量备份。

## 5. 踩坑：mailmap 的两种写法，两次都错

第一版写 `xingchen <新邮箱> <旧邮箱>`（省掉 Old Name）→ 两条规则匹配同一个旧邮箱，
**后写的盖先写的**，147 个 `xingchen` 全被改成 `星尘`。

第二版改成只写邮箱 `<新邮箱> <旧邮箱>` → 解析反了，**名字变成了邮箱串**，邮箱没变。

第三版写全四段 `New Name <new> Old Name <old>`，两个作者名分开写，才对。

教训：mailmap 的简写形式看着省事，但同一旧邮箱有多条规则时行为不直观，
**写全四段、让 old name 参与匹配**才有确定性。改完必须查 `%an` 和 `%ae` 两列，只看一列会漏。

## 6. 善后

| 动作 | 结果 |
| --- | --- |
| force push main + v0.1.1 | ✅ 远端 `88586b6` / `553a9a3` |
| **删除远端 v0.1.0 标签** | ✅ 它指向旧提交 `a194322`，留着等于泄漏没清理 |
| 本地删标签 + `gc --prune=now` | ✅ 不可达对象 0、reflog 0、无 `refs/original` |
| 仓库级 `user.email` 改为 noreply | ✅ 否则下一次提交又把真实邮箱带进来 |

`docs/M4.48` 里还留着一处旧 SHA（`a194322`，0.1.0 安装包的冒烟输出），**不改** ——
那是当时的实测记录，改了就失真，读者查不到也不影响什么。

## 8. 以后

- **新仓库初始化时就先设 noreply 邮箱**，别等扫出来才改 —— 重写历史的代价全在这一步省掉。
- 本机其他项目（如 Minecraft mod 那边）仍是同一个个人邮箱，公开发布前同样要处理。
- 隐私扫描脚本留在 `D:\CoPulProbe\privacy_scan.py`（仓库外），下次可复用。
