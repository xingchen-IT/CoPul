# M4.32 全屏护航：巡检提速 + 抢顶可判读

> 起因：用户报「我现在正在运行悬浮窗模式，但是 MC 全屏还是没有显示」（M4.31 已修过一次抢顶空窗）。
> 本次**没能复现"完全不显示"**，先把"能确定不是原因"的部分排除，再补一条可判读的日志，
> 让下次报障时能一眼分清是「抢顶」还是「渲染/位置」。

## 1. 现场取证（用户报障当次，20:00 前后）

| 判据 | 实测 | 结论 |
| --- | --- | --- |
| MC 窗口 | `(0,0,2560,1600)` `WS_POPUP`，**无** `WS_EX_TOPMOST` | 真全屏、非独占（`DwmIsCompositionEnabled=True`） |
| 悬浮窗 | `(1855,0,2492,51)` `WS_EX_TOPMOST` | 位置、样式都正常 |
| Z 序 | 悬浮窗上面只有两个 1×1 的 `ThumbnailDeviceHelperWnd` | **没被任何可见窗口压住** |
| 12s × 10Hz 采样 | 120/120 拍「悬浮窗在最顶」 | 稳态无遮挡 |
| 15s（游戏置前台 + 抢顶后） | 像素全程 24~36（深色条在画） | 游戏前台时也在 |
| 亮场景对比度 | 条内 luma **80** vs 条外 **237** | **不是"看不清"**（用户也确认） |
| DWM cloaked | game 0 / float 0 | 没被 DWM 隐藏 |

即：在我能构造的所有状态里（含"模拟 MC 抢顶"：`SetWindowPos(HWND_TOPMOST)`），悬浮条都真的画在屏幕上。

## 2. 找到的两处真实弱点

### 2.1 抢顶事件不是每条路径都有 WinEvent

M4.31 挂的是 `FOREGROUND / REORDER / LOCATIONCHANGE`。实测 `SetWindowPos(HWND_TOPMOST)`
只发 `LOCATIONCHANGE`；但日志里 20:04:22 那次仍是 `reason=poll` —— 说明还有路径一条事件都不发，
只能靠 1Hz 巡检兜底，最坏空窗 1 秒。**游戏里就是"闪一下不见了"**。

修法：前台是铺满显示器的外部窗口时，把巡检周期 1000ms → **250ms**（其余时候维持 1Hz）。

判据走 `Monitors.IsFullscreenForeground`：一次 `GetForegroundWindow` + `GetWindowRect` +
`GetMonitorInfo`（约 30µs），**故意不用那套带 QUNS 旁证的全屏状态机** —— 这里只要便宜的宽松信号，
误判的代价只是多跑几次巡检。桌面/任务栏/本进程窗口按类名排除。

### 2.2 「当时到底有没有认成全屏游戏」没有日志

新增 `[topmost] fs-guard on/off`（只在切换时记一条）。这是下次判障的第一判据：

- 报障时段里有 `fs-guard on` → 程序确实认成游戏全屏，问题在抢顶或渲染；
- **一条都没有** → 前台压根没被认成"铺满屏的外部窗口"，立刻换到渲染/位置那条线排查，
  不要再调 Z 序。
