# M4.10 悬浮窗竖向（整条旋转 90°）阶段报告

- 日期：2026-10-31
- 范围：6.1 悬浮窗形态扩展 —— 竖向排列
- 用户原话：`为悬浮窗添加一个竖向排列的模式`，随后明确
  `我想要的使原本那种横向的效果旋转90度变成竖向的（字体也要旋转）`

---

## 1. 背景与一次返工

第一版把"竖向"理解成"六格改成纵向堆叠"（每格压成一行，主值靠左、次值靠右）。
用户看到后的要求是：**要的是同一根条整体转 90°，文字跟着转**，不是重新排一遍版。

两者差别很大：

| | 纵向堆叠（已废弃） | 整条旋转（本版） |
| --- | --- | --- |
| 格子内部 | 重新排版（两行压成一行） | 原样不动 |
| 文字朝向 | 仍然是正的 | 随条旋转 90° |
| 条的长短边 | 34 宽 × 约 200 高 | 34 宽 × 381 高（= 原条长） |
| 阅读顺序 | 每行"值 + 标签"横读 | 从上到下逐格，读法与横条一致，只是转了 90° |

废弃的那版在 XAML 里多出一整套 `ColumnPanel`（6 个 `Grid` + 12 个 `TextBlock`），
以及 `VerticalRowWidth` / `RowGap` 两个依赖属性、三组竖向专用常量。
本版全部删除 —— 只有一套横向面板，竖向与否只由一个旋转变换决定。

## 2. 实现

### 2.1 一个 LayoutTransform 搞定

```csharp
Shell.LayoutTransform = _vertical ? new RotateTransform(VerticalAngle) : null;
```

- **必须是 `LayoutTransform`**。`RenderTransform` 不参与测量，窗口仍是横的，
  旋转后的内容会被窗口矩形裁掉（半个条直接不见）。
  `LayoutTransform` 会把"旋转后的需求尺寸"报给父级，窗口才跟着从 381×34 变成 34×381。
- **旋转要在设窗口尺寸之前落地**。`SizeToContent` 是按"当前布局结果"量测的，
  先量再转会先得到横向尺寸，窗口随后跳到正确大小，肉眼能看见一闪。
- 角度是常量 `VerticalAngle = 90`（WPF 正角 = 顺时针）。想反过来（条首在下、文字头朝左）
  改成 `-90` 即可，**不需要动任何尺寸逻辑** —— 旋转只交换长短边，34 这个短边不变。

### 2.2 尺寸：短边定死、长边交给内容

| 方向 | 短边 | `SizeToContent` |
| --- | --- | --- |
| 横向 | 高度 = 34 × 档位 | `Width`（六格宽度之和） |
| 竖向 | 宽度 = 34 × 档位 | `Height`（旋转前的条长） |

和横向完全对称，不用手算 381 这种数字。内边距、圆角跟着一起转：
横向的左右各 10 DIP 在竖向下变成上下各 10，两端留白与横条一致。

### 2.3 两处必须跟着改的地方

1. **`PlaceAtBottomLeft`**：竖向时 `Window.Height` 是 `NaN`（交给 `SizeToContent`），
   直接用它算底边会得到 `NaN`，窗口消失。改用 `ActualHeight`，取不到时按短边兜底。
2. **`PrePlaceBeforeShow`**（全屏自动切换的 Show 之前预摆位）：竖向的"高"是旋转前的条长，
   用 `EstimateVerticalLength()` 按「六格宽 + 列间距 + 两端内边距」算 —— 这是一串定值，不是猜，
   误差只剩边框那 2 像素。

### 2.4 顺带补的探针

| 探针 | 用途 |
| --- | --- |
| `--float-vertical` | 启动即竖向（不落盘，见 `glassOverride`） |
| `--float-menu-probe` | 走真实路由事件 (`RaiseEvent`) 打开右键菜单 + 对条内一点做 `InputHitTest`，把 `isOpen` / `hit` / `Shell` 尺寸 / `PointToScreen(0,0)` 写进 sidecar |

后者存在的原因：右键菜单是独立 popup，落点由元素变换算；而真实鼠标在本机随时被使用者挪走
（M4.3 踩过），只能靠"事件链 + 命中测试"两个信号判断旋转有没有打断交互。

## 3. 验收

### 3.1 尺寸：短长边精确互换

| 档位 | 横向 | 竖向 |
| --- | --- | --- |
| 100% | 381×34 | **34×381** |
| 125% | 476×43 | **43×475**（取整） |
| 150% | 571×51 | **51×571** |

`--shot-screen` sidecar 原文（100%）：

```
size : 34×381 DIP
scale: 竖 100% FPS=34.0 CPU=44.0 GPU=44.0 RAM=74.0 VRAM=78.0 NET=44.0 font=13.0/10.0 h=34.0
```

### 3.2 实拍

- `preview-m4.10-row-vs-col.png` —— 左横右竖并排：字段顺序一一对应
  （FPS → CPU → GPU → 内存 → 显存 → 网络），竖向就是横条顺时针转了 90°，
  每个数字与文字的朝向都跟着转，无一格缺失。
- `preview-m4.10-vertical-scales.png` —— 100 / 125 / 150 三档竖向并排，
  相对比例一致、文字没有被裁切。
- `preview-m4.10-vertical-full.png` —— 100% 档整条。

### 3.3 交互没被旋转打断

```
place: menu-probe: isOpen=True hit=Border shell=381x34 origin=(1989,0)   ← 横向
place: menu-probe: isOpen=True hit=Border shell=381x34 origin=(2040,0)   ← 竖向
```

- `isOpen=True`：`RaiseEvent` 的右键路由事件能把菜单打开，两个方向都成立。
- `hit=Border`：条内一点能被命中（不是 `null`）→ 右键与拖动走同一套命中测试，都还能用。
- 竖向的 `origin=(2040,0)` = 窗口左边 1989 + 窗口宽 51：`PointToScreen(0,0)` 正确地把
  Border 的本地原点映射到了旋转后的右上角 —— 这是坐标换算做了变换的证据，
  也正是右键菜单落点所依赖的那条链。

### 3.4 设置页

「悬浮窗外观 → 排列」横向 / 竖向，改即生效即落盘；
`--settings --settings-probe "layout:column"` 验证配置 `"FloatVertical": true` 落盘。

## 4. 已知限制

1. **旋转后的文字失去 ClearType**。WPF 对非轴对齐文字退回灰度抗锯齿，字边缘比横条略软。
   这是旋转渲染的固有代价，不是字号或绑定问题；100% 档下实测仍清晰可读。
   不接受的话只能放弃"文字跟着转"，改回纵向堆叠的排版（已废弃的上一版）。
2. **右键菜单的落点没有实拍**。探针只能证明"菜单打开了、条能被点中"，
   菜单自身是独立 popup，在无人操作时会被自动关闭，抓不到画面。
   落点计算走 `PlacementTarget.PointToScreen`，与变换无关，风险低但未拍到实据。
3. **竖向位置没有单独的默认规则**。仍沿用"左边界 + 12、底边 + 12"，
   切到竖向后由 `EnsureFullyVisible` 夹回工作区。贴哪条边由用户拖动决定，吸附规则不变。
