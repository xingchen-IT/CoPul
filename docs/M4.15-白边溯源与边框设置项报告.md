# M4.15 那圈白边的真身，与「边框」设置项

- 日期：2026-10-31
- 范围：6.1 悬浮窗 —— 静止时那圈描边
- 用户原话：`有些时候还会出现白色的边框，你来排查一下原因`
- 结论：白边**不是 DWM 画的，是我们自己画的**，两轮修复都没碰过它。已改为用户可调（无 / 淡 / 明显）。

当前显示缩放 **150%**（`GetDpiForSystem() = 144`）。

---

## 1. 白边是谁画的

### 1.1 先用排除法砍掉 DWM

M4.13 抹掉的是 `DWMWA_BORDER_COLOR`（`WS_THICKFRAME` 的附加产物）。它到底还灵不灵，
用一个对照就能判：`--float-border none`（抹掉）与 `default`（放回系统边框），
同一块 `#0A0A0A` 纯色底上 `--shot-screen --shot-pad 10` 各拍一张：

```
border=none     外沿峰值 50
border=default  外沿峰值 51
```

**两者无差别** —— DWM 那条边框确实已经被 M4.13 抹掉了，它不再是白边来源。
（RTB 拍不到 DWM 层，这一组必须走 `--shot-screen`。）

### 1.2 剩下的就是我们自己的 `Shell.BorderBrush`

`--shot`（RTB，走视觉树）在窗口左右缘量到 2 像素 `#FFFFFF`：

| 浓度档 | 描边 RGB | **alpha** |
| --- | --- | --- |
| level 1（极透） | `#FFFFFF` | **36（14%）** |
| level 4 / 7 | `#FFFFFF` | 31（12%） |
| 拖动中 | `#FF7FB8` 粉 | 255（不透明） |

> 第一版取证脚本只读了 RGB，看到 `#FEFEFE` 就以为是"近乎纯白"。
> PNG 存的是**非预乘** RGBA —— 白色是白的，但 alpha 只有 31~36。**浓度必须读 alpha 通道**。

### 1.3 屏幕上到底有多显眼

纯深底 `#0A0A0A`（亮度 8）+ 屏幕抓屏 + 窗口中部横切面：

| 浓度档 | 背景 | 边缘峰值 | 条内底色 | 白边比条内亮 |
| --- | --- | --- | --- | --- |
| **level 1（极透，用户当时配置）** | 8 | **50** | 16 | **+34** |
| level 4 | 8 | 44 | 16 | +28 |
| level 7 | 8 | 44 | 17 | +27 |

白边比周围亮 **3 倍**。

## 2. 为什么是"有些时候"

三个因素叠加，缺一个就不显形：

### 2.1 背景深浅决定可见度

这圈描边是**叠加白**（alpha 混合），背景越深越跳；桌面是浅色时它与背景同色，就看不见了。
所以"有时候有、有时候没有"实际上跟着壁纸/当前窗口走。

### 2.2 用户当时用的是「极透」档（`FloatGlassLevel: 1`）

`ApplyGlass` 里有一句：

```csharp
_edgeIdle = blurOnly ? _edgeHover : _edgeNormal;   // 极透档借用悬停档
```

理由是极透档几乎没有底色，怕用户找不到窗口的四条边 —— 结果是这一档的静止描边
被提到悬停档（14%，比其他档的 12% 更白），**且没有底色压着，直接叠在桌面上**。
实测它正是最亮的一档（+34）。

副作用：极透档下 `_edgeIdle` 与 `_edgeHover` 撞成同一个值，**悬停反馈完全消失**。

### 2.3 拖动结束那一刻最扎眼

拖动中是**不透明粉**（`#FF7FB8` @255），松手立刻变回**半透明白**（@36）。
从实心到 14%，反差很大 —— 这正是 M4.14 用户说的"白边"。
M4.14 只改了"拖动中"的颜色，没动松手后回去的那个值。

---

## 3. 改动：把选择权交给用户

"描边要多亮"没有唯一正确答案：深色玻璃上要勾出边界就得叠白，而叠白在深色桌面上就是白边。
与其替用户决定，不如让他自己挑。

| 文件 | 改动 |
| --- | --- |
| `Sdk/ConfigStore.cs` | 新增 `FloatEdgeMode`（`none` / `faint` / `normal`，默认 `normal`） |
| `Themes/Palette.xaml` | 新增 `BrushGlassEdgeFaint`（黑 5%）/ `BrushGlassEdgeDarkFaint`（白 5%）/ `BrushGlassEdgeNone`（全透明） |
| `FloatWindow.xaml.cs` | 新增 `EdgeMode` 属性、`NormalizeEdgeMode`、`EdgeBrushFor`、`ApplyEdge()` |
| `FloatWindow.xaml.cs` | `ApplyGlass` 里"极透档提亮"改为统一走 `ApplyEdge()`，且**只在 `normal` 档提亮** |
| `FloatWindow.xaml` | 右键菜单新增「边框」子菜单（无 / 淡 / 明显） |
| `SettingsWindow.xaml` / `.cs` | 悬浮窗卡片新增「边框」一行（`Edge_Checked`）+ `LoadFromConfig` 回读 |
| `App.xaml.cs` | `--float-edge none\|faint\|normal`；该参数纳入"自测不落盘"名单 |

### 3.1 两个设计决定

**「无」用全透明画笔，不是 `BorderThickness = 0`。**
改厚度会让窗口宽度少 2 DIP（`SizeToContent` 的条子会突然变窄），而且拖动那圈粉色也画不出来了。

**三档只管静止时那一圈**，悬停与拖动照旧给反馈。
否则选了「无」就彻底没有边界感 —— 鼠标进窗口、按住拖动都毫无回应。
"静止看不见"不该顺带把"被抓住了"一起抹掉。

**「淡」「无」档下极透档不再提亮。** 之前那句 `blurOnly ? hover : normal` 会把用户的选择改回去。

### 3.2 取证

同一块深底 + `--shot-screen`，横切面亮度（背景 8）：

| 边框档 | 边缘峰值 | 条内底色 | 高出的亮度 |
| --- | --- | --- | --- |
| `normal` | 50 | 16 | **+34** |
| `faint` | 28 | 16 | **+12** |
| `none` | 16 | 16 | **+0** |

探针输出（三档 × 拖动，`--float-drag-probe release`）：

```
edge=none    during=#FFFF7FB8  after=#00000000  idle=#00000000  hover=#24FFFFFF
edge=faint   during=#FFFF7FB8  after=#0DFFFFFF  idle=#0DFFFFFF  hover=#24FFFFFF
edge=normal  during=#FFFF7FB8  after=#24FFFFFF  idle=#24FFFFFF  hover=#24FFFFFF
```

三档下拖动**都是粉色** —— 「无」档也能看出"被抓住了"。

设置页截图 `preview-m4.15-settings-edge.png`：悬浮窗卡片第 5 行「边框」，无 / 淡 / 明显，
默认「明显」，无重叠错位。

## 4. 编译与验收

```
dotnet build CoPul.sln -c Release   →  0 个警告  0 个错误
```

运行副本 `D:\CoPulRun\CoPul.dll` 已同步。

| 项 | 命令 | 结论 |
| --- | --- | --- |
| 白边归属 | `--float-border none` vs `default` + `--shot-screen` | 50 vs 51，DWM 那条已被 M4.13 抹掉 |
| 描边浓度 | `--shot`（RTB，读 **alpha**） | `@36`（极透）/ `@31`（其他） |
| 三档亮度 | `--float-edge none\|faint\|normal` + 深底抓屏 | +34 / +12 / 0 |
| 拖动仍可见 | `--float-drag-probe release` | 三档 `during` 都是 `#FFFF7FB8` |
| 设置页 | `--settings --shot` | 「边框」行渲染正常 |

## 5. 备注

- **读 PNG 描边浓度必须看 alpha 通道**：`--shot` 输出 Pbgra32，PNG 存的是非预乘 RGBA，
  只看 RGB 会得到 `#FEFEFE`（"近乎纯白"）这种完全误导的结论。
- 本机桌面有自我持续置顶的游戏浮层，`--shot-screen` 偶发被切（本次 `none` 档第一次拍到背景 142
  而不是 8）。**背景亮度不对就要重拍**，不能拿那张图下结论。
