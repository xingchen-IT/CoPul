### 1.2 采集成本（核心数据）

LHM 的 `Update()` 以**硬件为单位**，无法只更新单个传感器。这是成本失控的根源。

| 硬件 | 非管理员 | **管理员** | 折合单核占用（1s 刷新） |
| --- | --- | --- | --- |
| Motherboard | 0.00 ms | 0.00 ms | 0% |
| **CPU** | 1.93 ms | **218.10 ms** | **21.8%** |
| Memory（总量） | 0.00 ms | 0.00 ms | 0% |
| Memory（单条 SPD） | — | 1.26 / 1.32 ms | — |
| **GPU (NVIDIA)** | 76.64 ms | **76.93 ms** | **7.7%** |
| GPU (Intel 核显) | 0.42 ms | 0.42 ms | — |
| **Storage #1 / #2** | — | **18.31 / 12.16 ms** | **3.1%** |
| **合计（若全量 LHM）** | — | **≈ 326 ms / 轮** | **≈ 33%** |

对比：如果按需求文档第 11 章的目标（1s 挡位 CPU ≤ 0.5%），**实测超标 66 倍**。

### 1.3 三个致命发现

**① NVIDIA GPU 走 LHM 比直连 NVML 慢约 19000 倍**

| 路径 | 单次耗时 |
| --- | --- |
| LHM `NvidiaGpu.Update()`（33 个传感器逐个调 NVAPI） | **76.93 ms** |
| NVML 直连（占用+温度+显存+功耗 四项全读） | **0.004 ms** |

原因不是硬件慢，是 LHM 为**每个传感器单独发一次 NVAPI 调用**，33 个传感器就是 33 次往返。
**结论：GPU 采集必须绕过 LHM，直接 P/Invoke `nvml.dll`。** 这样 GPU 完全可以进 T0（50ms 档）。

**② CPU 温度代价高达 218 ms / 次**

提权前 1.93 ms、提权后 218 ms —— 差的 216 ms 全是内核驱动读 MSR 的往返开销。
31 个温度 + 20 个频率 + 4 个功耗，每个都要一次 ring0 调用，累计 218 ms。

直接把 LHM 的 CPU 更新放进采集循环，1s 挡位就是 21.8% 单核占用，用户会看到"监控软件自己把 CPU 吃掉 20%"。
**这是本报告最重要的一条：CPU 温度无法按原设计进入 T1（500ms）。**

**③ 硬盘温度读到 0.00 °C（假值，不是真温度）**

管理员下 Storage 硬件枚举成功，两块的 `Composite Temperature` 都返回 **0.00**，而 `Warning Temperature 69 / Critical 74` 说明 SMART 数据已拿到。
说明 LHM 的 NVMe 温度读取在这台机器/这个驱动版本上失败，返回了默认值 0。
**任务栏模式的"硬盘温度"目前没有可用数据源。**

## 3. 对需求文档 v0.2 的影响

### 3.1 必须修订的条目

| 位置 | 原文 | 应改为 | 依据 |
| --- | --- | --- | --- |
| 4.0 分级表 T1 | CPU 温度、功耗归 T1（floor 500ms） | **CPU 温度/功耗单列，floor 由实测决定；无法进 T1** | 218 ms/次，500ms 档等于 43% 单核 |
| 4.0 分级表 T0 | GPU 占用/显存列在 T0，来源 NVML | 保留 T0，但**必须注明"绕过 LHM，直接 NVML"** | LHM 路径 76.93 ms |
| 4.0 分级表 T2 | 硬盘温度 floor 1000ms | 保持，但**注明当前无有效数据源** | 读到 0.00 °C |
| 4.2 注 | "v1 仅承诺 NVIDIA 完整支持" | 补充实测：Intel 核显只有频率和共享内存，无温度/功耗/占用 | 19 个传感器中含 0 个 Temperature |
| 4.1 C09 | 列出风扇转速 | **本机不可用，需在诊断页明示"笔记本无 SuperIO"** | 0 个 Fan 传感器 |
| 4.1 C06 | 列出当前频率 | 可用，但依赖提权 | null → 4505 MHz |
| 11 | 启动到首帧 ≤ 1.5s | 改为"≤ 1.5s 显示窗口；数据就绪 ≤ 4s（后台初始化）" | Open() 3532 ms |
| 13.5 | 提示驱动风险 | **升级为已确认事实**：必须管理员，非提权时 31 个温度传感器全 null | 两次对照运行 |

### 3.2 架构层面要加的三条硬约束

| 编号 | 约束 | 理由 |
| --- | --- | --- |
| A-08 | **GPU 采集禁止走 LHM**，直接 P/Invoke `nvml.dll`（nvmlDeviceGetUtilizationRates / GetTemperature / GetMemoryInfo / GetPowerUsage） | 实测 19000 倍差距 |
| A-09 | **CPU 温度采集独立成"重采集"任务**，与 T0 高频循环分离，用独立低频线程 + 缓存值读出 | 218 ms 不能阻塞任何 200ms 级循环 |
| A-10 | 采集器**启动必须异步**：窗口先出，驱动加载与硬件枚举在后台线程，期间 UI 显示"—" | Open() 3.5s |

### 3.3 需要你决策的两件事

> **2026-10-27 已定案：Q-19 选 A（自研 MSR 直读）、Q-20 选 A（自研 NVMe `Get Log Page`）。**
> 落实位置：需求文档 v0.3 的第 3.2 章（A-08~A-12）、4.0（分级表重排，T1 floor 500→200ms）、4.1 / 4.2 / 4.4（指标数据源改写）、15.4（取舍依据）、16（R7/R8/R9 新增）。
> 本节保留决策当时的原始对比，不作修改——它是"当时为什么这么选"的证据。

#### Q-19 CPU 温度怎么采？（决定性能天花板）

| 方案 | 单次成本 | 温度刷新 | 代价 |
| --- | --- | --- | --- |
| **A. 自研 MSR 直读**（借 LHM 已装的 ring0 驱动，读 `IA32_PACKAGE_THERM_STATUS`） | 目标 < 1 ms | 可到 1s 甚至 20Hz | 需要写 ring0 调用封装，约 1–2 天；驱动复用 LHM 的，不额外签 |
| **B. 接受 LHM 218ms，固定 5s 采集** | 218 ms / 5s = 4.4% 单核 | **5s 一次** | 零开发量；但"温度"这个字段反应迟钝，且常驻 4.4% 仍不算轻 |
| **C. 降到 10s** | 2.2% 单核 | 10s 一次 | 更省，但基本只能看趋势，不能看瞬时 |
| **D. 用 PDH 的 `\Thermal Zone Information(*)\Temperature`** | < 0.1 ms | 1s | 精度差（整 1°C、部分机器不暴露），但够显示 |

**我的建议：A 为目标，B 作为 M1 的过渡。** 先用 B 把三模式跑通，M4 再换 A。
不建议 D ——"温度不准"对一个监控软件是硬伤，宁可慢也不要错。

#### Q-20 硬盘温度怎么采？（决定任务栏字段是否落地）

| 方案 | 可行性 | 代价 |
| --- | --- | --- |
| **A. 自己发 NVMe `Get Log Page`（IOCTL_STORAGE_QUERY_PROPERTY + ATA/NVMe PassThrough）** | 高，admin 下稳定 | 约 1 天，需按 NVMe/SATA 分别处理 |
| **B. 改用 LHM 的 `Storage` 但只取 SMART 原始值自己解析** | 中 | LHM 已把 0 写死，绕不开 |
| **C. v1 先不做硬盘温度，任务栏该字段显示"—"或隐藏** | 立即 | 功能缺一块 |

**我的建议：C 先兜底（M1 不阻塞），A 在 M4 补。** 任务栏的"硬盘温度"是原始需求里明确要的，但它是唯一必须依赖 SMART 直读的字段，值得单独排期，不值得卡住整个 M1。

## 4. 复现方法

```bash
# 1. 编译（用户级 SDK，未污染系统）
SDK="C:/Users/user/.workbuddy/binaries/dotnet-sdk/8.0.404"
cd tools/m0
"$SDK/dotnet.exe" build -c Release

# 2. 非管理员跑（看基线 / 确认哪些指标依赖提权）
export DOTNET_ROOT="$SDK"
"$SDK/dotnet.exe" bin/Release/net8.0-windows/win-x64/M0Probe.dll m0-report-noadmin.txt

# 3. 管理员跑（弹 UAC）
powershell -Command "Start-Process '$SDK/dotnet.exe' -ArgumentList 'bin\Release\net8.0-windows\win-x64\M0Probe.dll','m0-report-admin.txt' -WorkingDirectory '$PWD' -Verb RunAs"
```

依赖源：`tools/m0/NuGet.config` 已指向华为云镜像（官方 nuget.org 在本机不可达）。
