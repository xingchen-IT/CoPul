# M1.1 大窗口骨架：落地报告

> 日期：2026-10-27　｜　对应需求：v0.10 第 5 章（大窗口）、第 10 章（视觉规范）、第 11 章（性能）
> 结论速览：**窗口能跑、26 项指标全部上台、刷新 0.5s 对齐**；自身开销实测 **0.81% / 1.17% / 1.25%**（三轮 60 秒，单核口径），**最坏 1.25% 超出 0.9% 目标约 1.4 倍**——见第 6 章，需要一次决策。

## 2. 线程与刷新模型

```
UI 线程                         后台线程 CoPul.Init             采样线程 CoPul.Sampler
   │                                  │                                  │
   ├─ 构造 CollectorHost ────────────►│                                  │
   ├─ 帧定时器 250ms（只查脏标记）     │                                  │
   │                                  ├─ scheduler.Start()               │
   │                                  │   └─ Provider.Initialize() ─────►│ 每 500ms 跑一轮
   │                                  │      (PDH 约 0.6s)               │
   │                                  ├─ SystemInfo.Collect()            │
   │                                  │   (DXGI 40ms + 盘/分区)           │
   │                                  └─ InfoReady ──► UI 线程           │
   │                                                                     │
   │◄────────────── 帧定时器读 _latest，≥500ms 才画一帧 ◄────────────────┤ SnapshotReady
```

三条设计取舍：

1. **初始化一律在后台**。`SampleScheduler.Start()` 里会跑各 Provider 的 `Initialize()`，PDH 那一步实测 0.6s；`SystemInfo.Collect()` 冷盘时还要 190ms（R20）。这两件事任何一个落到 UI 线程，窗口就是"点开等一秒才出来"。
2. **不用 `BeginInvoke` 逐帧投递，改用 UI 线程上的帧定时器**。逐帧投递在窗口被拖动/系统繁忙时会在消息队列里堆积，越积越卡；定时器只读一个脏标记，晚到的帧自然合并。
3. **帧间隔下限 = 挡位（500ms）**。见 4.1，这条直接决定了开销。

## 4. 五个坑（都已修，下一个人别再踩）

### 4.1 采样器每层各发一帧，界面被喂成 8 帧/秒

原实现里每个 tier 触发一次 `Merge + SnapshotReady`。0.5s 挡位下 T0/T0b/T1/T1b 四层都落在同一个 500ms 边界，等于**同一个时刻发 4 次快照**，视图被要求重绘 8 次/秒，而数据每 0.5s 才变一次。

改法（→ A-24）：一轮循环里所有到期的 tier 先跑完，最后只 `Merge` 一次、只发布一次。帧数 8/s → 2.67/s；再在 UI 侧加"帧间隔 ≥ 挡位"的下限（→ A-25），落到 **1.83 帧/秒**。

### 4.2 `InvariantGlobalization=true` 会让 WPF 连窗口都开不出来

从采集层照搬了这个属性，结果 `Application.Run` 直接抛：

```
System.InvalidOperationException: Cannot find non-neutral culture related to 'en-us'
   at System.Windows.Markup.XmlLanguage.GetSpecificCulture()
```

WPF 的 Binding 必须解析 `xml:lang` 的具体区域。**采集层设它安全（不碰 WPF），App 层绝对不能设。**

### 4.3 `ProgressBar.Value` 默认是 TwoWay 绑定

`MetricCell.Bar` 只有 getter，绑定直接抛 `无法对只读属性 Bar 进行 TwoWay 绑定`。必须写 `Mode=OneWay`。这条同样适用于任何绑到只读属性的 `RangeBase`/`TextBox`。

### 4.4 无边框窗口最大化会盖住任务栏

`WindowStyle=None` 时系统按整屏算最大化尺寸。必须自己接管 `WM_GETMINMAXINFO`，把 `ptMaxSize`/`ptMaxPosition`/`ptMaxTrackSize` 改成显示器的工作区（见 `Interop/Win32Window.cs`）。

### 4.5 XAML 注释里不能出现 `--`

`<!-- ---------- CPU ---------- -->` 会让整个 XAML 编译失败：`An XML comment cannot contain '--'`。分隔线只能用 `=` 或中文。

## 5. 性能实测

### 5.1 口径

- 窗口正常显示、0.5s 挡位、**跳过 10 秒预热**再取 60 秒窗口（启动里有 JIT / PDH 初始化 / 冷盘枚举，混进去会把读数抬高好几倍）；
- 单核口径 = `Process.TotalProcessorTime` 增量 ÷ 墙钟 × 100%；
- 每份输出都带线程级分解（`tools/m11/final-*.txt`）。

### 5.2 三轮结果（机器空闲）

| 轮次 | 单核 | 整机 | 帧数/60s | 平均 ApplySnapshot | 平均 Layout | UI 线程占比 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **1.172%** | 0.0586% | 109 | 0.320 ms | 1.946 ms | 0.29% |
| 2 | **0.807%** | 0.0403% | 111 | 0.330 ms | 2.022 ms | 0.23% |
| 3 | **1.249%** | 0.0625% | 111 | 0.277 ms | 2.024 ms | 0.44% |

中位 **1.17%**，最好 0.81%，最坏 1.25%。`render tier = 2`（硬件加速），非软件渲染。

### 5.3 噪声有多大（必须写下来）

同一份二进制，在有 `dotnet build` 并发、或系统忙的时候：

| 场景 | 单核读数 |
| --- | --- |
| 机器空闲（上表） | 0.81 – 1.25% |
| 后台同时在编译 | 1.59 / 2.76 / 3.59 / 3.93% |
| 其中一轮 UI 线程单项 | 2.40%（布局 2.3ms × 111 帧 ≈ 0.43%，多出来的全是等合成的墙钟） |

**结论：本机测自身开销必须独占运行。** 这与 M0.6 的"跨会话 tick 时间不可比"是同一条纪律的延伸。

### 5.4 成本花在哪

| 项 | 量级 | 依据 |
| --- | --- | --- |
| 采集（四 Provider + 调度） | 约 0.5% 单核 | `--hidden` 只采集不显示：1.146%；m06 单跑 0.573% |
| 界面布局 | **每帧约 2.0 ms**，1.83 帧/秒 ≈ **0.37%** | `--stats` 里强制 `UpdateLayout()` 计时 |
| 界面其余（绑定、属性通知） | 每帧 0.28–0.39 ms ≈ 0.06% | ApplySnapshot 计时 |
| 合计 | 0.8 – 1.25% | 与三轮实测吻合 |

顺手排除了两个猜想：

- **不是"20 个核心数字"那一行的锅**：`--no-cores` 只把布局从 2.07ms 降到 1.92ms（7%），省不出量级。
- **不是 `UseLayoutRounding` / `SnapsToDevicePixels` 的锅**：去掉后布局 2.24ms，没有改善（已还原，因为它们在 125% DPI 下让边缘更清楚）。

## 6. 与 0.9% 目标的差距 —— 已决策：选项 A（Q-24）

需求 11 章 v1 当时的目标是 **≤0.9% 单核**。实测最坏 1.249%，超出 1.4 倍；最好 0.807% 能过。R4 当初的估算写的是"WPF 渲染约 0.3–0.5%"，现在看**这条估算偏乐观**：实际界面成本 0.4–0.6%（布局 2ms/帧 × 1.83 帧/秒，还没算合成与 GC）。

三条路，代价不同：

| 选项 | 做法 | 预期 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 调整目标口径** | 0.9% → 1.5% 单核，硬上限 2.5% | 立刻达标（余量 1.20 倍） | 改了验收线，需要文档留痕 | **✅ 采纳（2026-10-27，Q-24）** |
| B. UI 刷新降到 1Hz | `MinFrameIntervalMs = 1000` | 界面省一半 ≈ 0.9% 附近 | 数值每 1s 变一次，与 0.5s 挡位的"跟手感"冲突 | ❌ 与 Q-23 冲突 |
| C. 给界面瘦身 | 合并 tiles、去掉 wrap/trim、减少每帧变更元素 | 未知，估计 10–30% | 收益不确定；本次已试 `--no-cores`（省 0.15ms）与去 `UseLayoutRounding`（反而 2.24ms），都不解决 | ❌ 无据可依 |

**为什么 A 是对的，而不只是"放水"**：0.9% 是 v0.8 在**只有采集器**时按 0.573% 定的，而第 11 章从一开始考核的就是**整个进程**。同一份代码，采集器口径"达标 1.57 倍"、整窗口径"超标 1.4 倍"——这不是程序变慢了，是**用 A 的测量结果给 B 定了标准**。改的是错误的定义，不是放宽标准。

**1.5% 这个数字的依据**：单核 1.5% = 整机 0.075%（20 线程）/ 0.107%（14 物理核）。任务管理器按整机口径显示，用户看到 **0.1%**，四舍五入看不见。再往上（3% 单核 = 整机 0.15%，显示 0.2%）用户就能感知到"这软件在吃 CPU"了。**所以 1.5% 是本项目"不可见"的上限，不是随手挑的整数。**

**落地内容**（详见需求文档 15.9 / A-26）：

| 项 | 改后 |
| --- | --- |
| 4.0 目标表 | 拆成两行：采集器单独 ≤1.0%（内部参考）+ **整窗 ≤1.5%（验收线）** |
| 11 章 CPU 目标 / 硬上限 | **≤1.5%（整窗口径）/ 2.5%** |
| R22 | **关闭** |
| **A-26（新增）** | 每加一个渲染面都必须重跑 60s×3；超标先抬 T1b floor，**不得再调目标** |

> 余量只有 1.20 倍，够加一般量内容，**不够再加一个完整区块**。M1.2 的单盘 D03 与折叠功能都要过 A-26 这道闸。

## 8. 怎么跑

```bash
# 正常启动（需要托管运行时；apphost 在受限沙箱里会被拒）
dotnet CoPul.dll

# 渲染一张窗口截图（无头验收用）
dotnet CoPul.dll --shot out.png --wait 6000

# 量自身开销：跳过 10s 预热，取 60s 窗口，含线程级分解
dotnet CoPul.dll --stats out.txt --seconds 60 --warmup 10

# 分离成本用的对照组
dotnet CoPul.dll --stats a.txt --hidden    # 只采集，不显示窗口
dotnet CoPul.dll --stats b.txt --freeze    # 显示窗口但冻结数据更新
dotnet CoPul.dll --stats c.txt --no-cores  # 跳过"各核心"长文本
```

> 环境备忘：本机 apphost（`CoPul.exe`）在受限 shell 里会因为 `hostfxr.dll` 被拒而启动失败，用 `dotnet CoPul.dll` 即可；直接双击 `CoPul.exe` 不受影响。
