# M4.31 悬浮窗置顶改为事件驱动

- 日期：2026-11-02
- 需求：用户「我再游玩 mc 时悬浮窗不能一直在最上层」
- 结论：**不是我们的窗口掉了 topmost，是游戏自己挤进了 topmost 组**
- 范围：悬浮窗的置顶链路（`FloatWindow.GuardTopmost` + 新增 `Interop/ZOrderWatch`）。大窗口、设置页、任务栏条不动

---

## 1. 先证伪："我们的窗口根本没置顶"

用户报障时（19:15）那一份实例是 19:12:51 启动的、最新构建，且配置 `FloatAlwaysOnTop=true`。实测：

| 取证 | 结果 |
| --- | --- |
| Z 序采样 32 秒（0.1s × 320 拍，`tools/zorder-blocker.py`） | **一次都没被压住**，悬浮窗始终在最顶 |
| 整屏抓图（`shot-full.py` + 裁剪） | 悬浮窗正常叠在游戏画面上（30 FPS / 41% / 48% 那一条） |
| 窗口样式 | `float ex=0x000188`（含 `WS_EX_TOPMOST`）、`game ex=0x00040010`（**不含**） |

所以稳态是好的 —— 问题只在**切换的那一瞬间**。

## 2. 复现：按 F11 那一刻

写 `tools/f11-transient.py`：50ms 一拍同时记 Z 序链 + 浮窗内部三点像素亮度（玻璃底亮度 < 80，游戏画面 > 120），中途自动按两次 F11。

旧构建（19:45 那次）：

| t | 被压 | 暗点/3 | 亮度 | 说明 |
| --- | --- | --- | --- | --- |
| 0.02 | 否 | 3 | 29,29,31 | 正常 |
| 1.64 | **是** | **0** | 159,141,155 | 浮窗看不见了 |
| 2.17 | 否 | 3 | 76,75,58 | 被拉回来（0.53s 后） |

同一次抓到的关键数字：

```
floatEx 0x000188（一直带 TOPMOST）
gameEx  0x040010  →  0x040018        ← 多出来的 0x8 就是 WS_EX_TOPMOST
上面是谁 [GLFW30] 'GregTech Leisure-增强版'
```

**根因**：GLFW 进全屏会给自己的窗口加 `WS_EX_TOPMOST`。于是两个窗口同处 topmost 组，`SetWindowPos` 谁后提谁在上；我们的保底巡检是 1Hz，所以每次游戏提顶都要空窗 0.5~1 秒才被拉回来 —— 用户看到的就是"它老不在最上层"。

## 3. 修法：把 1Hz 巡检换成事件驱动

### 3.1 哪个 WinEvent 才真的会来（实测，不是猜）

写独立探针监听 `0x0003..0x800B` 全段，手工把游戏窗口提一次：

| 动作 | 收到的事件 |
| --- | --- |
| `SetWindowPos(HWND_TOPMOST)`（MC 抢顶用的就是它） | **只有** `EVENT_OBJECT_LOCATIONCHANGE` × 19 |
| `SetForegroundWindow` | `LOCATIONCHANGE` × 13 + `OBJECT_REORDER` × 10 + 其它 |

第一版只挂了 `EVENT_SYSTEM_FOREGROUND` + `EVENT_OBJECT_REORDER`，实测量出来还是 571ms、日志全是 `reason=poll` —— **只挂 REORDER 等于没挂**，因为"自己提顶"这条路径一个 REORDER 都不发。

### 3.2 合并而不是限流

`LOCATIONCHANGE` 是高频事件（拖窗口、动画、悬停都在刷）。用"距上次 < 80ms 就丢掉"的限流会把整串事件连尾一起丢光，于是改成：

> 第一个事件排一次 **16ms 后** 的执行；期间再来的只合并。

既不会刷爆，也保证"变化之后 16~32ms 内一定跑一次"。钩子回调本来就在 UI 线程，定时器回调投回构造时捕获的 `SynchronizationContext` 再碰窗口。

### 3.3 提顶判据从两条理由变成三条

| 理由 | 之前 | 现在 |
| --- | --- | --- |
| 被外部可见窗口压住 | ✔ | ✔ |
| `WS_EX_TOPMOST` 掉了 | ✘（会被上一条漏掉：style 掉了但恰好没窗口重叠时，"没被挡住"是真的） | ✔ |
| 都没有 | 不动 | 不动（常态，不做无意义的 SetWindowPos） |

同时去掉"本进程有窗口在前台就不抢"的早退。那条策略的原意是别压住设置页，但设置页压着悬浮窗时"上面那个是自家窗口"已经挡住了；而**"前台是自家的、上面压着的却是外部窗口（游戏 / 开始菜单）"**这个组合下，早退会让悬浮窗永远出不来 —— 正好是用户描述的症状。

## 6. 注意 / 遗留

- **游戏若"每帧"抢顶**，16ms 合并也追不上，会表现为高频闪烁。实测 MC 只在切换时抢一次，抢完我们稳住；真碰上这种游戏只能退到"渲染通道"层面（layered 窗口），不在本次范围。
- 本机常驻的桌面宠物 `DesktopCatInput`（pid 60580，全屏 TOPMOST）也会被同一套逻辑处理 —— trace 里能看到它当遮挡者的记录，属正常。
- 验收期间结束过用户正在跑的实例（`taskkill` 的 `//FI` 过滤没生效，把两个都杀了），**需要重新双击启动**。
- 下次再"看不见悬浮窗"，先看 `%TEMP%\copul-trace.log` 的 `[topmost]` 行：有 raise 且 `after=0x0` = 我们赢了；一条都没有 = 根本没被 Z 序挡住，那是渲染问题，别往置顶方向查。
