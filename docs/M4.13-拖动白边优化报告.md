# M4.13 拖动时那圈白边

- 日期：2026-10-31
- 范围：6.1 悬浮窗 —— 拖动过程中的边缘观感
- 用户原话：`悬浮窗移动时的白色边框非常不好看，你看看能不能优化一下效果`

---

## 1. 现象

拖动悬浮窗时，整条四周会亮起一圈白线，松手后又淡下去。截图 `preview-m4.13-before.png`
（改前，鼠标停在条上、深色壁纸区域）里能直接看到这圈高对比的白描边。

## 2. 两条来源，都要处理

### 2.1 主因：鼠标一进窗口，描边就从 12% 白跳到 22% 白

悬浮窗的描边不是画在窗口上的装饰线，而是 `Shell`（根 `Border`）的 `BorderBrush`，
深浅主题各一套：

| 主题 | 常态 | 悬停 |
| --- | --- | --- |
| 浅色 | `BrushGlassEdge` 黑 12% | `BrushGlassEdgeHover` 黑 24% |
| **深色（用户当前）** | `BrushGlassEdgeDark` **白 12%** | `BrushGlassEdgeDarkHover` **白 22%** |

鼠标进窗口时 `Shell_MouseEnter` 切换到悬停档 —— 这是给"可以点/可以拖"的反馈。

**问题在于拖动必然按住窗口，也就必然在窗口上**：`MouseEnter` 早就把描边换成了 22% 白，
于是整个拖动过程都在用最亮的那一档。深色玻璃底只有 25 luma，22% 白叠上去就是
25 + 0.22 × 230 ≈ 76，实测最外 2 像素正好是 **75**（常态 12% 时为 55）。同一位置的
一次 A/B：`--shot-screen --shot-pad 6` 下 `default / none` 两种边框设置，条内亮度一致 25，
只有最外 2px 是 55 与 75 —— 差值全部来自这层描边。

### 2.2 次因：DWM 给 `WS_THICKFRAME` 窗口画的那条 1px 边框

悬浮窗为了拿系统阴影给窗口加了 `WS_THICKFRAME`（M2 报告 2.11：影子只能这么来）。
副作用是 DWM 从此把它当"有框架窗口"，除了阴影还会在外沿画一条边框，颜色跟随主题。

这条边框平时看不见，但只要显式给它一个颜色就能抓出来 ——
`--float-border "#FF0000"` 之后窗口外沿出现 **1864 个纯红像素**，正好围成 70×408 的一圈：

```
b-none     red px = 0
b-default  red px = 0
b-FF0000   red px = 1864   x 30..100  y 30..437   ← 窗口矩形外沿 2px（1 DIP @150%）
```

静止时它很淡（默认色实测 55，比描边还暗），但拖动进入 move loop 时 DWM 会重绘框架，
它就成了另一层"白边"来源。

## 3. 改动

| 文件 | 改动 |
| --- | --- |
| `Themes/Palette.xaml` | `BrushGlassEdgeDarkHover` **白 22% → 白 14%**（`#38FFFFFF` → `#24FFFFFF`） |
| `FloatWindow.xaml.cs` | `Shell_MouseLeftButtonDown`：`DragMove()` 前后把描边压回常态，松手后按 `IsMouseOver` 恢复 |
| `Interop/Win32Window.cs` | 新增 `TryDisableDwmBorder` / `TryResetDwmBorder` / `TrySetDwmBorderColor`（`DWMWA_BORDER_COLOR` = 34） |
| `FloatWindow.xaml.cs` | `EnableSystemShadow` 末尾按 `BorderMode` 设置边框色；新增 `DwmBorderDiag` |
| `App.xaml.cs` | `--float-border none\|default\|#RRGGBB`；sidecar 增加 `border:` 一行 |

两处叠加后，拖动中的描边从 **22% 白（luma 75）降到 12% 白（luma ≈ 55）**，
并且不再有 DWM 那条额外的 1px 框架边。

### 3.1 为什么不动 `WS_THICKFRAME`

它是系统阴影的唯一开关（M2 已证伪别的路线）。阴影是"这扇窗浮在桌面上"的主要线索，
比一条 1px 边框重要。所以只是把边框的**颜色**抹掉，框架本身留着。

### 3.2 顺序：先加框架，再抹边框

`WS_THICKFRAME` 正是 DWM 判断"要不要画边框"的依据。先设边框色再改 style，
那次 style 变更会把边框带回来 —— 所以 `TryDisableDwmBorder` 必须排在
`SetWindowLongPtr + NotifyFrameChanged` 之后。

## 4. 自测开关

| 开关 | 用途 |
| --- | --- |
| `--float-border none` | 默认。抹掉 DWM 1px 边框 |
| `--float-border default` | 恢复系统主题色，用于 A/B |
| `--float-border "#FF0000"` | 涂成纯红。**判定"拖动白边到底归谁管"的最快手段** |
| `--no-shadow` | 完全不加 `WS_THICKFRAME`（没有阴影也没有框架边） |

## 5. 取证限制（诚实记一笔）

改后没能在拖动过程中拍到可信截图。原因不是代码，是本机环境：

1. **同机另有一个正在运行的 CoPul 实例**（用户自己开着的，`CoPul.exe` PID 46408，
   主窗口与悬浮窗都在）。`FindWindow` 按标题取到的是它，于是"窗口位置"在两处之间跳，
   截图时深时浅 —— 前几轮 `h-idle` / `v-after` 尺寸突然变成 1298×1391 就是这么来的。
2. **整屏 `BitBlt` 抓不到 DWM 合成层**：拖动帧（`red-d01..d06`）里一个红像素都没有，
   而同样的红边框用 `--shot-screen`（`SaveWindow`）就能拍到 1864 个 —— 所以拖动中的画面
   只能靠窗口自身渲染的内容，DWM 画的那一层漏掉。

因此本版的结论建立在两件事上：**改前改后同条件的最外 2px 亮度差（55 / 75）**，
以及**红边实验证明 DWM 边框确实画在窗口外沿**。最终观感请实际拖一下确认。

## 6. 还嫌亮的话，往下还有两档

| 档 | 做法 | 效果 |
| --- | --- | --- |
| 再淡一档 | `BrushGlassEdgeDarkHover` 14% → 12%（和常态一样） | 悬停完全没有亮度反馈，只剩鼠标形状变化 |
| 彻底去掉 | `Shell.BorderThickness = 0`（深色主题下） | 边界只靠阴影，玻璃"悬浮感"更强，但深色底上边界会糊 |

当前选 14% 是折中：还能看出"这块能拖"，但不至于像给条子镶了银边。
