# M4.23 全屏切换：防抖档位（0.5s / 1s / 2s / 3s）

需求原话：

> 做一下其它挡位的效果（1s，2s，3s等）
> 不用把切回改成这么详细的，不用两个时间确认，直接用一个设置选项更改时间挡位就行了

承接 M4.22：抖动已修（点悬浮窗不再被判成非全屏），剩下的是**门限本身只有一个值** ——
需求 8.4 定的"进入 800ms / 退出 500ms"是写死在代码里的常量，用户没法按自己的习惯调。
这一版把门限做成一个**可调档位**（进入与退出共用同一个数），并逐档做了真机取证。

编译：0 警告 0 错误（Release，`dotnet build CoPul.sln -c Release`）。

---

## 1. 改了什么

| 文件 | 改动 |
|---|---|
| `Sdk/FullScreenAutoSwitch.cs` | `EnterHold`/`ExitHold` 两个常量 → 单个实例属性 `HoldMs`；档位表 `HoldChoices = {500, 1000, 2000, 3000}`、`NormalizeHold()`、`SetHold(int)`、`ApplyConfig(enabled, holdMs)` |
| `Sdk/ConfigStore.cs` | 新增 `FullScreenHoldMs`（默认 **1000**） |
| `SettingsWindow.xaml` | 「全屏时自动隐藏」下加**一行**分段按钮：**切换确认** 0.5s / 1s / 2s / 3s |
| `SettingsWindow.xaml.cs` | `FsHold_Checked`（落盘 + 立即生效）、`SelectHoldSegment()`、探针命令 `fshold:<ms>` |
| `App.xaml.cs` | `SettingsContext.SetFullScreenHold(int)`；启动时 `ApplyConfig(开关, 档位)`；`--fs-hold <ms>`（命令行覆盖，不落盘） |
| `Probes/FullScreenLiveProbe.cs` | 头部打印当前档位；每次迁移打一行 `---- <t>ms 迁移 #n：<内容> ----` |
| `Probes/FullScreenSwitchProbe.cs` | 步骤**按档位自适应**（原来写死 6 步，2s/3s 档下会假失败） |
| `Probes/FullScreenProbe.cs` | 伪造链路 A/B 同样按档位算步数；旧"800ms/500ms"注释更新 |
| `tools/fake-fullscreen.py` | 新增 `--restore <秒>`：缩窗后再铺满，模拟"Alt+Tab 出去看一眼又回来" |

**默认值**：8.4 原定进入 800 / 退出 500，合成一档后取 **1000**。
退出那一侧比原来稳一倍（挡得住 1s 内的切出），进入那一侧只慢 200ms —— 换一个档位就能调回去。

档位值由 `FullScreenAutoSwitch` 一处定义，UI 与探针共用；手改配置写了 1500 也不会被拒绝
（`NormalizeHold()` 归一到最接近的档，与 `NormalizeScale` 同一套取舍）。

> 为什么不拆成"进入"和"退出"两个数：这两个数怎么配合，本质上只有"快 vs 稳"一个取舍。
> 给用户两个数，等于让他替我们做设计。一个档位解决的是同一个问题：**瞬时状态要不要被当真**。

## 2. 各档实测：门限真的按值生效

真机场景不变（`tools/fake-fullscreen.py` 另进程造无边框铺满屏窗口当"游戏"，CoPul 用 `--fs-live-probe` 真实跑）：

```
游戏全屏 ──▶ Taskbar ──档位──▶ Float(auto) ──游戏销毁──▶ 档位 ──▶ Taskbar
                                   ↑
                           中途 Activate 悬浮窗（模拟点它一下，M4.22 回归）
```

脚本 `D:\CoPulRun\fs-hold.sh <档位ms>`，汇总 `fs-hold-summary.py`。
绝对时刻不可比（CoPul 每次启动耗时不同），所以量的是 **"首次观测到该状态" → "真的迁移"** 的耗时，
采样粒度 500ms，实测值应落在 `[档位, 档位+500]`：

| 档位 | 进入实测 | 退出实测 | 迁移次数 | 终态 |
|---|---|---|---|---|
| 500 ms | 605 ms | 498 ms | 2 | Taskbar ✓ |
| **1000 ms（默认）** | 1089 ms | 1002 ms | 2 | Taskbar ✓ |
| 2000 ms | 2125 ms | 2000 ms | 2 | Taskbar ✓ |
| 3000 ms | 3124 ms | 3001 ms | 2 | Taskbar ✓ |

四档**全部只有 2 次迁移**（进一次、退一次），说明 M4.22 的修复在各档位下都还成立 ——
中途那次"点一下悬浮窗"没有触发任何多余回落。

## 3. 档位的实际价值：短暂切出去还回不回得来

只看"门限准不准"说明不了该选哪一档。真正决定体验的是**防抖能不能挡住瞬时状态**：
打游戏时 Alt+Tab 出去看一眼（1.5s）再切回来，档位够长就**不会**回落任务栏。

新增 `--restore` 让假游戏缩窗 1.5s 后重新铺满，脚本 `D:\CoPulRun\fs-flicker.sh <档位ms>`：

| 档位 | 迁移次数 | 实际发生什么 |
|---|---|---|
| 500 ms | **3** | 缩窗 0.5s → 回落任务栏；恢复全屏 → 又切回悬浮窗（**一次多余抖动**） |
| 1000 ms | **3** | 同样抖（1.5s 已超过门限） |
| 2000 ms | **1** | 稳在悬浮窗，全程不动 |
| 3000 ms | **1** | 稳在悬浮窗 |

**怎么选**（写进了设置页说明文字）：

- 打游戏为主、很少切屏 → 0.5s / 1s，反应最快。
- 经常 Alt+Tab、或游戏爱弹窗口 → **2s**（1.5s 的切出就挡住了）。
- 常被 PPT/浏览器 F11 误触发、或切出去很久才回来 → **3s**。

## 4. 界面与探针

设置页「常规」页，「全屏时自动隐藏」下方就一行（截图 `m423b-settings.png` 已确认只有一行、无残留、无截断）：

```
切换确认   [0.5s] [1s✓] [2s] [3s]
须连续全屏/非全屏这么久才切换：越长越不容易被切屏、弹窗带偏，代价是切换反应也慢一点。
```

改档位**立即生效**（下一轮判定就按新门限走），不重置已经攒着的计时 ——
用户是在观察中调档位，清掉计时反而会让"刚从 2s 调到 0.5s"这一下不立刻切过去。

| 命令 | 用途 |
|---|---|
| `--fs-hold <ms>` | 命令行覆盖档位做取证（**不落盘**） |
| `--fs-live-probe <txt> --fs-live-end <ms>` | 真机采样，头部打印档位、每次迁移打一行 |
| `--settings-probe "scroll:1300,fshold:2000"` | 设置页点档位并把四个按钮的选中状态打到 stdout |

⚠️ `fshold` 会**真的写用户配置**（走的是同一条 `Checked` 路径）：取证完记得核对 `config.json`，
本次已把 `FullScreenHoldMs` 还原回 1000。

## 6. 一句话结论

防抖门限从"写死的两个常量"变成"一个可调档位（0.5s/1s/2s/3s，默认 1s）"，进入与退出共用同一个数；
真机实测四档门限均按值生效（误差 ≤500ms 采样粒度），且 **2s/3s 能挡住 1.5s 的 Alt+Tab 切出**，
而 0.5s/1s 会多出一次"回落又切回"的抖动 —— 这就是档位存在的意义。
