# M2.1 性能复测报告（A-26 重启条件）

- 日期：2026-10-29
- 触发：A-26 规定「每次增加渲染面都必须重跑」，M2 新增了悬浮窗 + 毛玻璃 + DWM 投影三个渲染面
- 被测版本：`ab7d54c`（M2 视觉与交互全部落地）
- 原始数据：`tools/m15/`（索引见 `tools/m15/INDEX.md`）
- **一句话结论：本轮仍不能判定绝对值（环境不满足前提，R24 第四次），但同环境 A/B 证明 M2 没有引入整窗回归；悬浮窗自身折算约 0.3–0.45% 单核。**

---

## 1. 为什么这次不能用老口径

m14 的规矩是「60s × 3 取最坏，机器接近空闲（整机 < 10%）」。本轮机器上跑着《异环》与《终末地》：

| 指标 | 实测 | A-26 要求 |
| --- | --- | --- |
| 整机 CPU | **47%–58%**（持续） | < 10% |
| `HTGame.exe`（异环） | **609% 单核 ≈ 6 个核**，8.9 GB 内存 | — |
| GPU 占用 / 显存 / 温度 | 81% / 6864 of 8188 MiB / 82 °C | 空闲 |
| 内存 | 88.9%（28.1 / 31.6 GB） | — |

按老口径测出来的绝对数字，跟 m14 的 2.603% 不可比——**而且比 m14 那次（29.9%）还差一倍**。所以本轮换了三套互补的测法，只保留「同一时段内可比」的量。

---

## 2. 方法

### 2.1 配对交替（`run_pairwise.py`）

四个条件在同一时段内交替跑，反平衡 3 轮（`A B C D / D C B A / A B C D`），每个条件 3 次取中位：

| 代号 | 命令 | 含义 |
| --- | --- | --- |
| `hidden` | `--stats X --hidden` | 无窗口，纯采集器基线 |
| `main` | `--stats X` | 大窗口（用户配置 853×509，趋势/温度折叠） |
| `float` | `--stats X --float --glass-level 2` | 悬浮窗（含毛玻璃 + DWM 投影） |
| `float-noshadow` | `--stats X --float --glass-level 2 --no-shadow` | 同上但关掉投影 |

40 s 测量 + 8 s 预热。**为什么不是 60 s**：配对法只取差值，40 s 的时间分辨率（0.039% 单核）够用，多出来的时间用于增加轮数抵消漂移。绝对值本来就不采信。

> 预热 8 s 不是随手定的：12 s 短测读到 9.361%，同一个条件跑到 40 s 只有 2.460%。差值来自 WPF/D3D 建管线与 DWM 建合成层的**一次性成本**，预热短了会把固定开销摊进稳态。

### 2.2 同代码 A/B（worktree 拉 m14 基线）

复测一开始就撞上一个吓人的数字：`main` 的 **Layout 12.7 ms/帧**，而 m14 报告是 4.2 ms。3 倍的布局成本像是严重退化。

用 `git worktree` 把 m14 当时的代码（`2a83919`，10-28 00:12，FPS 区块之前）拉出来单独编译，在**同一台机器、同一配置、同一尺寸**下跑：

| 版本 | 单核 | Layout | ApplySnapshot | UI 线程 |
| --- | --- | --- | --- | --- |
| 当前 `ab7d54c`（含 FPS 区块 + M2） | **6.323%** | 12.711 ms | 0.797 ms | 2.81% |
| m14 基线 `2a83919`（FPS 之前） | **6.443%** | 14.326 ms | 0.906 ms | 2.62% |

**旧代码反而更慢。** 所以 12.7 ms 与代码无关，是环境造成的——游戏把 6 个核吃满，UI 线程与采集线程都要抢 CPU、抢 LLC，单帧布局的墙钟时间被拉长 3 倍。

顺带得到一个换算倍率：m14 在干净环境下 `main` 是 2.603%、Layout 4.2 ms，同一代码在现在环境是 6.443%、Layout 14.3 ms → **单核倍率 2.48、Layout 倍率 3.41**。后文折算用这个。

### 2.3 DWM 侧采样（`dwm_side.py` / `dwm_levels.py`）

`--stats` 只统计 CoPul 进程自身，而 accent acrylic 的模糊是 **DWM 在合成阶段**做的，不计入 CoPul。只用 CoPul 的数字会把毛玻璃说成免费。所以另起一轮，用 psutil 同时采 `dwm.exe` 的 CPU 时间。

**这一路失败了**，原因见 4.3。

## 3. 结果

### 3.1 配对矩阵（40 s / 8 s，2026-10-29 17:07–17:17）

| 条件 | 三次单核 | 中位 | Layout | 整机中位 |
| --- | --- | --- | --- | --- |
| `hidden` | 1.835 / 1.874 / 2.070 | **1.874%** | 0.010 ms | 47–57% |
| `main` | 5.037 / 5.897 / 6.865 | **5.897%** | 12.8–13.7 ms | 45–56% |
| `float` | 2.460 / 2.928 / 3.358 | **2.928%** | 2.4–2.8 ms | 52–58% |
| `float-noshadow` | 3.124 / 3.241 / 3.475 | **3.241%** | 2.4–2.5 ms | 52–58% |

| 配对差值 | 数值 |
| --- | --- |
| `main` − `hidden` | **+4.023 pp** |
| `float` − `hidden` | **+1.054 pp** |
| `float-noshadow` − `hidden` | **+1.367 pp** |
| `float` − `float-noshadow`（投影的代价） | **−0.313 pp** |

**投影那一行是负数，说明测不出来。** 0.31 pp 的差在 ±0.5 pp 的噪声内，符号都不可信。`float` 三次（2.46/2.93/3.36）与 `float-noshadow` 三次（3.12/3.24/3.48）区间几乎重叠，没有任何方向性。

**`float` 的 Layout 2.4–2.8 ms 是谁的？** `--float` 时大窗口从未 `Show()`，但 `--stats` 打印的是 `MainWindow.LayoutTotalMs`。原因是 WPF 的 `UpdateLayout()` 走 **per-Dispatcher 的 `ContextLayoutManager`**，会把同一 Dispatcher 上所有脏视觉树一起处理——所以这 2.4 ms 就是**悬浮窗自己的布局成本**（`--hidden` 时没有窗口，所以是 0.010 ms）。这是个有用的副产品：悬浮窗的布局成本可以直接从这一列读出，约 `2.5 ms × 1.9 帧/s ≈ 0.48% 单核`（污染环境）。

### 3.2 成本拆解

用 3.1 的差值除以 2.2 的倍率，粗略还原到干净环境：

| 项 | 污染环境 | 折算（÷2.48 ~ ÷3.41） |
| --- | --- | --- |
| 采集器（`hidden`） | 1.874% | ≈0.75%（m14 实测 1.171%，说明采集以 I/O 等待为主，受 CPU 争抢影响小，倍率只有 1.6） |
| 大窗口渲染面 | +4.023 pp | ≈1.2–1.6 pp（m14 实测 UI 差值是 1.38 pp，吻合） |
| **悬浮窗渲染面（本轮新增）** | **+1.054 pp** | **≈0.3–0.45 pp** |
| DWM 投影 | 测不出（< 0.3 pp 噪声） | — |

悬浮窗那 1.05 pp 里，布局占 0.48 pp、`ApplySnapshot`（六字段文本更新）约 0.14 pp、其余是合成与提交。

### 3.3 DWM 侧：测不出来，如实记录

第一轮 8 次（25 s/次）：

| 条件 | 两次 | CoPul | dwm |
| --- | --- | --- | --- |
| `hidden` | 1、8 | 1.50 / 1.50% | 25.50 / 24.94% |
| `main` | 4、5 | 6.19 / 6.62% | 27.62 / 25.87% |
| `float` | 2、7 | 2.56 / 2.50% | **39.06 / 37.37%** |
| `float-noshadow` | 3、6 | 3.44 / 2.87% | **44.75 / 29.44%** |

`float` 让 dwm 多了 13 pp，看着像「毛玻璃的代价」——但 `float-noshadow` 两次自己就差了 **15.3 pp**。

于是补了第二轮档位验证（`--glass-level 1` 无模糊 / `7` 重模糊，22 s/次）：

| 条件 | 两次 dwm |
| --- | --- |
| `hidden` | 31.32 / **16.05** |
| `lv1`（无模糊） | 36.01 / 28.12 |
| `lv7`（重模糊） | 24.43 / 22.16 |

**同一个 `hidden` 条件两次差 15.3 pp，比窗口带来的差异还大**，而且「重模糊」那组反而最低。这说明 dwm 的读数完全由游戏合成负载决定（GPU 81% 满载、显存仅剩 1.3 GB，DWM 随时可能在 GPU 与 CPU 合成之间切换），窗口效应被淹没。

**结论：本环境下 DWM 侧不可测。** 第一轮那个「+13 pp」是时间漂移，不是因果——如果按它下结论，会把毛玻璃的成本夸大成 0.65% 整机。这条弯路留在报告里，因为下次换机器时还得先确认 dwm 读数自己稳不稳。

## 4. 判定

| 项 | 结论 |
| --- | --- |
| 整窗绝对值是否 ≤1.5% | **未判定**。A-26 前提（整机 <10%）不成立，本轮整机 47–58%，R24 **第四次**复现 |
| M2 是否引入整窗回归 | **否**。同环境 A/B：当前 6.323% vs m14 基线 6.443%，当前反而更低 |
| Layout 4.2 → 12.7 ms 是否退化 | **否**。旧代码在同环境是 14.3 ms |
| 悬浮窗的代价 | **≈0.3–0.45 pp 单核**（折算），量级合理，与「一个小窗口 + 12 个文本 / 1.9 帧每秒」相符 |
| DWM 投影的代价 | **测不出**（< 0.3 pp 噪声）；未发现异常证据，但也不能宣称「零成本」 |
| 毛玻璃在 DWM 侧的成本 | **测不出**（dwm 读数自身不稳，见 3.3） |

### 4.1 与 Q-25「接受现状」的关系

Q-25 记录的是「m14 复测 2.6% 单核、下限 ≈1.97% 已越线，三案暂缓、接受现状」。本轮**不改变这个结论**，但补上了它缺的一块：

- m14 那个 2.6% 里**不含** M1.4c/d/e 的 FPS 区块，也不含 M2 悬浮窗。本轮 A/B 证明 **FPS 区块 + M2 没有让大窗口变贵**（6.323 vs 6.443），所以 2.6% 这个基线现在仍然有效；
- 悬浮窗是**另一个形态**（和大窗口二选一，`Hide()`/`Show()` 切换），它自己约 0.3–0.45 pp。两者不叠加成 3%——用户实际只会看到其中一种。

### 4.2 这条结论的边界

1. 折算倍率（2.48 / 3.41）是从**一次** A/B 得出的，本身有误差；
2. `main` 用的是用户当前几何 853×509 且趋势/温度折叠，与 m14 的 820×1230 全展开不同口径，所以 `main` 的绝对数字不能直接对上 m14；
3. DWM 侧完全缺失，毛玻璃的真实成本仍是一个开口——**换到干净机器重测时必须把 dwm 一起测**，否则会漏掉本项目最大的一块未知。
