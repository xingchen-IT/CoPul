## 1. 为什么需求里早就有网络，界面却一直没它

需求文档 4.5 定义了 5 项网络指标（N01–N05），7.4 也把它们列进了任务栏字段，
但 **5.2 / 5.3 的大窗口章节从头到尾没有网络区块** —— 布局图是 CPU / GPU / 内存 / 硬盘四块，
字段清单里也只有这四块。M1.1 按 5.3 搭骨架，于是网络被整体漏掉，
采集层虽然早在 M0.6 就跑通了 N01/N02/N03，界面却无处安放。

v0.14 已补上这一处文档缺口（5.2 布局图 + 5.3 字段清单）。

## 3. 三个实现决策

### 3.1 N05 是字符串，不能塞进 MetricSnapshot

`MetricSnapshot` 只装 `double`（`Set(MetricId, double, ...)`）。为它加字符串通道会污染整个快照结构，
而 N05 每秒只要读一次。所以走旁路：`OsProvider.ActiveNicName` → `CollectorHost` → UI 每帧读属性。
引用赋值在 .NET 上是原子的，读到上一帧的值最多晚 0.5 秒。

### 3.2 N04 不另起 10 秒节奏

需求 4.5 写「采集间隔 10000ms」，但那指的是**探测统计窗口**，不是发布频率。
丢包率是 `PingLoop` 写、采集线程读的滚动窗口，读取成本在噪声内，
没必要为它单开一个 10s 组（那只会让 T2 组多一个空转的调度位）。

### 3.3 速率单位必须自适应

固定用 MB/s 时空闲显示 `0.0`，看不出还有没有流量；固定用 KB/s 时跑满会显示 `10240.0`。
阈值取 1 MB/s，由 `Fmt.RateAuto` 同时给出数值与单位。
因此 `MetricCell.Unit` 从只读改成可写 —— 这是本次唯一一处对既有组件的改动。

## 4. 实测

### 4.1 界面读数（普通权限，Wi-Fi 连接）

| 字段 | 读数 |
| --- | --- |
| 活动网卡 N05 | `Intel® Wi-Fi 6 AX201 160MHz` |
| 下行 N02 | 6.3 KB/s |
| 上行 N01 | 2.5 MB/s |
| 延迟 N03 | 15 ms |
| 丢包率 N04 | 0 % |

网卡名原本显示为 `Intel[R] Wi-Fi 6 AX201 160MHz`：**PDH 实例名不能含 `® ™ ©`**，
Windows 用 `[R] [TM] [C]` 转义，展示前必须还原，否则是半截商标。

### 4.2 上下行方向交叉验证（关键）

界面出现「上行 2.5 MB/s、下行 6 KB/s」这种反常读数，必须排除方向接反：

```
$ curl https://speed.cloudflare.com/__down?bytes=30000000
  code=200  bytes=30000000  speed=4064855 B/s   用时 7.64 s

网卡 WLAN 累计差值：
  ReceivedBytes  +36.72 MB  → 4.81 MB/s
  SentBytes      +20.72 MB  → 2.71 MB/s
```

下载时 RX 涨 36.72 MB，**方向与界面「下行」一致，未接反**。
TX 同步涨 20.72 MB 偏高（正常 ACK 只占 1–2%），说明本机的确存在并发上传：

```
idle WLAN  RX = 5.3 KB/s   TX = 510.5 KB/s
进程 IO 写速率：workbuddy 11026 KB/s、msedgewebview2 3538 KB/s
```

即：界面那 2.5 MB/s 上行是**真实流量**（当时 `workbuddy` 进程 IO 写 11 MB/s），
只是 0.5 s 窗口的瞬时值高于 4 s 平均值，看起来才显得突兀。

### 4.3 延迟与丢包

| 项 | 读数 | 说明 |
| --- | --- | --- |
| N03 延迟 | 14–15 ms | 目标 `223.5.5.5`，与 M0 实测的 14 ms 一致 |
| N04 丢包率 | 0 % | 滚动 10 次窗口，样本不足 10 次时也显示（有 1 次就出数） |
