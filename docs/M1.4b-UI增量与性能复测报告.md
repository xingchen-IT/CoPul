> 范围：M1.4 之后的四项 UI 增量（趋势图纵轴刻度、温度趋势区块、窗角圆角、崩溃日志）＋ 本轮 A-26 整窗性能复测。
> 日期：2026-10-28　｜　对应需求文档：v0.16　｜　原始输出：`tools/m14/`

## 2. 复测方法

严格沿用 A-26 / R24 的三条纪律：

- **指标**：进程自身 CPU 时间 / 墙钟 / 逻辑核数（单核口径），60 秒窗口，10 秒预热，同一进程内连续跑；
- **重复**：3 轮以上取最坏值；
- **前提**：机器必须接近空闲（任务管理器 CPU < 10%）。

窗口几何：改成新版默认 **820×1230、八区块全展开**（配置 `WindowHeight` 由 860 改为 1230），与本机 2560×1600 / 150% 缩放的实际可用区相关（见 3.3）。

命令（`src/CoPul.App/bin/Release/net8.0-windows` 下）：

```
dotnet CoPul.dll --stats <out.txt> --seconds 60 --warmup 10
```

对照组额外加 `--hidden`（只采集、不显示），或用配置 `CollapsedBlocks` 折叠指定区块。

### 2.1 环境（这次又不满足前提）

后台负载由 `tools/m14/sample_load.py` 每 3 秒采样一次，全程 56 个样本：

| 指标 | 数值 |
| --- | --- |
| 整机 CPU（全核） | **中位 29.9%，区间 21.5% – 55.9%** |
| 持续占用者 | `python.exe`（`pip install pyinstaller`）≈ 100%（1 整核）、`WorkBuddy.exe` 48–82%、`wallpaperui.exe`（Wallpaper Engine）39–52%、`msedgewebview2.exe` 39–42%、`DeepSeek Harness.exe` 43–73%（00:19 后加入） |
| 折算 | 常驻约 3–4 个核忙 = 整机 15–20% |

**A-26 的前提（< 10%）不成立，因此本轮同样只能记「未判定」**——这是 R24 的第三次复现。但与 M1.2 那次不同，这次有两条**同批次内可比、与背景负载无关**的旁证（见 3.2），足以给出方向性结论。

## 3. 结果

### 3.1 整窗（窗口显示）

| 轮次 | 单核 | 整机 | CPU 时间 | Layout | ApplySnapshot | 帧数/60s | 窗口 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | **2.603%** | 0.1302% | 1562 ms | 4.200 ms | 0.449 ms | 115 | 820×1230 |
| 2 | **2.550%** | 0.1275% | 1531 ms | 4.365 ms | 0.370 ms | 115 | 820×1230 |
| 3 | 4.048% | 0.2024% | 2453 ms | 5.592 ms | 0.461 ms | 113 | 820×1019 |

中位 **2.603%**、最坏 **4.048%**，对 1.5% 验收线分别是 **1.74 倍 / 2.70 倍**（硬上限 2.5% 也被越过）。

第 3 轮明显是噪声（同分钟整机 33–36%、`DeepSeek Harness` 三进程同时起），不能当最坏值用——但**前两轮 2.55–2.60% 本身就已经超线**，不是噪声导致的假超标。

### 3.2 同批次对照（成本拆解）

| 组 | 配置 | 时长 | CPU 时间 | 单核 | 差值 |
| --- | --- | --- | --- | --- | --- |
| 显示 | 全展开 | 60 s | 1562–2453 ms | 2.550–4.048% | — |
| 隐藏 | 全展开 | 60 s | 703 ms | **1.171%** | UI ≈ **1.38 pp** |
| 隐藏 | 全展开 | 40 s | 625 ms | 1.562% | — |
| 隐藏 | **进程区块折叠** | 40 s | 297 ms | **0.742%** | 进程组 ≈ **0.82 pp** |
| 隐藏 | 趋势+温度折叠 | 40 s | 406 ms | 1.015% | 两张折线图 ≈ **0.55 pp** |

三条结论：

1. **采集侧已从 0.62% 涨到 1.17%（M1.2 同条件 0.624%）**。增量几乎全部来自 M1.4 的进程组：折叠它直接掉到 0.742%。M1.4 用独立探针估的是 0.40%，本轮实测 **0.4–0.8%**——负载高时 PDH 通配符展开（`GPU Engine(*)\Utilization Percentage`，456 实例）变慢，是估值的 2 倍。
2. **渲染侧成本同样翻倍**：Layout 从 M1.2 的 1.93 ms/帧涨到 **4.2–5.6 ms/帧**（×2.2–2.9），帧率仍是 1.9 帧/秒。按 4.2 ms × 1.92 帧/秒算，布局一项年化 ≈ 0.81% 单核，和实测 UI 差值的量级吻合。
3. **两张折线图不便宜**：折叠后省 0.55 pp。它们每 0.5 秒各画 120 点（含填充、两条折线、5 个刻度文本），并且会触发父级 `StackPanel` 重排——4.2 ms/帧里应该有相当一部分来自这里。

### 3.3 顺带发现：默认高度 1230 在高 DPI 屏被截断

第 3 轮报告的窗口是 **820×1019**，而配置写的是 1230。原因：本机 2560×1600 @150%，**DIP 工作区只有约 1067 高**，1230 被系统钳到 1019。

好消息是内容不丢——第 1 行 Grid 的 `*` 行是 `ScrollViewer`（`VerticalScrollBarVisibility=Auto`），超出的部分可以滚动。坏消息是"默认打开就带滚动条"不算好体验，且 `1230` 这个默认值在 150% 缩放的 1600p / 1080p 屏上都会触顶。**建议默认值改为按工作区截断（如 `min(1230, WorkArea.Height - 40)`），或直接降到 1000。**

## 4. 判定

| 项 | 结论 |
| --- | --- |
| 是否达标 1.5% | **测不出可信值**（机器整机 21–56%，A-26 前提不成立），按 R24 记「未判定」 |
| 是否退化 | **是，方向明确**。同批次对照显示：采集 0.624 → 1.171（+0.55）、Layout 1.93 → 4.2–5.6 ms/帧（+2.2 倍） |
| 干净环境会不会达标 | **大概率不会**。用本轮最小可信量做下界估算：采集 1.17 + 渲染 ≈0.8（仅布局项）= **≈1.97%**，已越过 1.5%；把渲染压回 M1.2 的 0.62 也只是 1.79%。**下限已经超线，不是"等机器空闲就能过"的问题** |

**所以本轮不是"再等等"能收口的**：`2.55%` 的前两轮数据落在同一条线上，且两条独立旁证（`--hidden` 差值、Layout 毫秒数）都指向同一方向。

## 5. 优化候选（按性价比排序，均不动目标线）

| 优先级 | 措施 | 预期收益 | 代价 |
| --- | --- | --- | --- |
| **P1** | **T2b floor 5000 → 10000 ms**（进程表改 10 秒刷新） | 采集侧 **−0.2 ~ −0.4 pp** | 进程表刷新变慢一倍；任务管理器本身也是 ~1s 级，10s 对"看谁在吃 CPU"仍够用 |
| **P1** | **折叠进程区块时不再展开 GPU Engine 通配符**（当前只在展开时采，但要确认折叠是整组停采而非仅不渲染） | 与上一条重叠 | 无 |
| **P2** | **各区块改固定行高**（`Height` 而非 `Auto`），图表给固定尺寸，避免 `StackPanel` 每帧把整棵树 measure 一遍 | 布局 **−1 ~ −2 ms/帧**（≈ −0.2 ~ −0.4 pp） | 文案换行/字号变化时不自适应，需要预留余量 |
| **P2** | **趋势图按"新点到达"才无效化**，而不是每次 `Refresh()` 无条件 `InvalidateVisual` | 布局与绘制各降一档 | 需保证暂停/恢复时不出现空帧 |
| **P3** | 温度图默认折叠（多数场景只看占用率） | 首屏 −0.3 pp 左右 | 用户要多点一次 |
| **P3** | 窗口默认高度按工作区截断（见 3.3） | 不省 CPU，只解决"默认带滚动条" | 无 |

按 P1 全部落地估算：采集 1.17 → **0.9 左右**，整窗 ≈ 1.7%；再叠 P2 的布局优化进 1.5% 以内是现实的，但**必须重跑 60s×3 才能算数**（A-26）。

## 6. 待办

1. **R24 保持开放**：本机连续三轮（M1.2 / M1.4 / 本轮）都没等到空闲窗口。要么挑一个纯空闲时段，要么在干净机器/虚拟机里测。
2. **A-31（新增）**：进程组采集成本必须进预算表，任何新增"全局枚举"型指标都要先报单轮耗时。
3. 优化 P1/P2 是否现在做，等作者决定；不做也不影响功能验收，只是性能线暂时不达标。
4. 需求文档 v0.16 已同步本轮结论（11 章实测回填 + 15.10 + A-29/A-30/A-31 + R24 补记）。
